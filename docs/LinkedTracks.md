# 链接轨道（构想）

> 状态：构想，作者 2026-10-12 提出。在 `.usth` 中的表示与导出 `.ust` 时的去向已于 2026-10-15 决定（见「补充建议」），其余的实现方式留待以后设计。现行实现仍是单轨，见 [`Roadmap.md`](Roadmap.md)「多轨设计」与 [`UsthFormat.md`](UsthFormat.md)。

## 动机

OpenUtau 与 Synthesizer V 那样的多轨工程，在一个工程中容纳多条可编辑的轨道，各轨道共用一条时间轴与一条曲速线。UTAU 的规范却把曲速与渲染都绑定在音符上：曲速是音符的 `Tempo` 字段，渲染以音符为单位进行，渲染缓存也按音符划分。几条轨道各有一串音符与各自的曲速，要让它们共用一条时间轴并保持同步，代价很高，也容易与 UTAU 的行为产生分歧。

## 构想

**一份工程只编辑一条 UTAU 轨道，其他内容以链接的方式放进工程。** 做法类似 Adobe Premiere Pro 与 After Effects 链接另一个项目（Dynamic Link）：被链接的项目在自己的窗口中编辑，链接方只把它当作一段素材使用，对方修改后随之更新。

- **链接轨道**：工程 A 的一条轨道链接工程 B（`.ust` 或 `.usth`），把 B 当作一段伴奏使用。A 只使用 B 的渲染结果，不编辑 B 的音符，因此两者的曲速不必一致。
- **音频轨道**：伴奏等普通音频文件。
- **同步**：在另一个窗口中编辑工程 B 并保存，A 中链接 B 的轨道随之更新。

## 优点

- 曲速与渲染仍按 UTAU 的规范绑定在音符上，每份工程内部只有一条时间轴，不存在曲速不一致的问题。
- `.usth` 可以自然地加入音频轨道与链接轨道。
- 名义上一份 `.usth` 仍只编辑一条轨道，与 UTAU 的单轨模型一致，不破坏与 UTAU 的兼容。

## 建议

以下是对构想的补充建议，均未经作者决定。

- **链接方只使用被链接工程的人声，不跟随其链接。** B 本身也可能链接了 C。A 只取 B 自己那条轨道的渲染结果，不取 B 的混音，这样链接永远只有一层，循环链接也就无从出现，不必另行检测。
- ~~**链接方不执行被链接工程的合成工具。**~~ 作者 2026-10-15 改为由 A 渲染 B，B 的合成工具须经信任，见下文「被链接工程的声音」。
- ~~**按时间而非 tick 对齐。**~~ 作者 2026-10-15 决定起点以 tick 表示，见下文「链接路径」。
- **在钢琴卷帘中以只读的淡色显示 B 的音符。** 多轨编辑的主要价值之一是对照其他声部写和声。B 的音符按 B 的曲速换算到时间，再按 A 的曲速换算到 A 的位置，只用于显示，不可编辑。
- **双击链接轨道即在新窗口中打开 B**，对应 Premiere Pro 的「编辑原始」。B 保存后，A 检测到其文件的修改时间变化，即更新链接轨道的显示与渲染结果。
- **链接工程与音频文件的路径，绝对路径与相对于 A 所在文件夹的路径都保存**（作者 2026-10-12 建议）。A 与被链接的文件一起移动时，相对路径仍然有效。只移动 A 时，绝对路径仍然有效。解析时先按相对路径，找不到再按绝对路径。两者都找不到时，轨道显示为离线，提供重新链接，而不是让 A 打不开。
- **导出 `.ust` 时只导出 A 自己的轨道。** 链接轨道与音频轨道可以写进 `_USTH_` 控制音符的载荷，这样 `.ust` 在 HelloUtau 中往返时链接不丢失，UTAU 则照常只看到一条轨道。作者 2026-10-15 决定这样做，见下文「导出 `.ust` 与控制音符」。
- **导出音频时分三种**：混音、只导出 A 的人声、分轨导出。

## 补充建议（2026-10-15）

以下除注明作者决定之处外，同样未经作者决定，部分回答了下一节的问题。

### 在 `.usth` 中的表示

**作者 2026-10-15 决定**：

- 链接与音频都放在 `tracks` 中的轨道里，每条轨道以 `type` 标明种类：`notes`（UTAU 的音符轨道，至多一条）与 `clips`（存放片段的轨道）。片段同样以 `type` 标明种类：`audio`（音频文件）与 `linked`（链接的工程），**同一条轨道中两种片段可以混放**，与 DSPX 和 OpenUtau 相同。此前建议的顶层字段 `links` 不采用。作者提出的 `midi` 改称 `notes`，因为这条轨道存放的是由合成工具渲染的 UTAU 音符，与轨道已有的字段 `notes` 对应。
- **`type` 必须写出**，轨道与片段缺少 `type` 时在读取时报错。
- **片段的种类**：起初为三种轨道（`notes`、`linked`、`audio`），作者 2026-10-15 改为在片段上区分，理由是一条伴奏轨道上可能同时需要音频与链接的工程。对照：DSPX 的轨道不分种类，片段分音频与歌声。OpenUtau 的轨道不分种类，part 存放在工程顶层的 `voiceParts` 与 `waveParts` 中，以 `trackNo` 指明所属的轨道。Synthesizer V 把伴奏轨道作为单独一种，只放一个音频文件（按记忆，未在本地核对）。
- **`version` 提升为 2**，任何新写出的文件都是版本 2。已发出的版本打不开新文件是应有的结果：旧版本的读取方拒绝版本号更高的文件，并报告文件由更新的版本保存（`Project.cpp` 的版本检查）。版本 1 的文件没有 `type`，读取时按一条音符轨道处理。
- **每条轨道都有名称、音量、声像、静音与独奏。** 音符轨道另有现有的 `voiceDir` 与 `notes`。混音参数属于工程的内容，随工程保存与撤销。
- **轨道的顺序即显示的顺序**，音符轨道可以在任意位置。

### 片段与链接路径

**作者 2026-10-15 决定**。`clips` 轨道的 `clips` 数组存放片段，每个片段以 `path` 记录被链接的文件，以 `start`、`clipStart`、`clipLength` 记录位置与裁剪。轨道的名称、音量、声像、静音与独奏留在轨道上。

**位置与裁剪以 tick 表示**，与 DSPX 相同：opendspx 的 `ClipTime` 以 tick 记录片段的位置 `pos`、长度 `length` 与裁剪 `clipStart`、`clipLen`，音频片段同样如此，播放时按曲速表换算为采样位置。`start` 是素材起点在时间轴上的位置，对应 DSPX 的 `pos`。`clipStart` 是可见部分相对于素材起点的偏移，`clipLength` 是可见部分的长度，为 0 时放到素材结束。伴奏通常对齐到小节，按 tick 记录时 A 改变曲速后伴奏仍从同一小节开始，与 DSPX 互转时也无需换算。A 的曲速只改变片段开始的时刻：音频片段的内容按音频原样播放，不被拉伸，链接片段的内容按被链接工程自己的曲速播放（见下文「曲速」）。OpenUtau 的位置同样以 tick 表示，裁剪（`skipMs`、`trimMs`）则以毫秒表示，本仓库不采用这种混用。此前「按时间而非 tick 对齐」的建议不采用。

```json
{
  "type": "clips",
  "name": "伴奏",
  "clips": [
    {"type": "audio", "path": {"relative": "../bgm/intro.wav", "absolute": "D:/songs/bgm/intro.wav"},
     "start": 0, "clipStart": 0, "clipLength": 0},
    {"type": "linked", "path": {"relative": "harmony.usth", "absolute": "D:/songs/harmony.usth"},
     "start": 7680, "clipStart": 0, "clipLength": 0, "usesHostSynthTools": false}
  ]
}
```

界面起初可以只支持每条轨道一个片段，格式从一开始就留出片段这一层，以后支持多个片段时无需再提升版本。

- **`relative` 相对于 `.usth` 所在的文件夹**，与工程不在同一个卷上而没有相对路径时不写出。
- **分隔符一律为 `/`。** `VoiceDir`、`Tool1` 等字段写作 `\`，是为了与 UST 互转时保持 UTAU 的写法，链接路径不进入 UST 的正文，没有这一约束。统一为 `/` 后，在 macOS 上保存的工程在 Windows 上仍可按相对路径找到文件，Windows 也接受 `/`。
- **解析时先按 `relative`，找不到再按 `absolute`。** 两者都找不到时片段为离线，提供重新链接，工程照常打开。
- **保存时两种路径都由实际找到的文件重新求出。** 内存中只记录找到的文件，因此按绝对路径找到时，保存一次即更正相对路径。离线的片段保存时两种路径原样写回，不丢失。
- **从未保存的工程只记录绝对路径**，第一次保存时求出相对路径。**另存为到其他文件夹时按新的位置重新求出相对路径**，否则新文件的相对路径仍指向旧的位置，这一点须有专门的测试。重新链接时两种路径都重新求出。
- **被链接的 `.ust` 没有声明 UTF-8、也没有 HelloUtau 的控制音符时**，链接时询问一次编码，记录在该片段的 `ustCharset` 中，与「不猜测编码」的规则一致（`CLAUDE.md`「编码」）。有控制音符时以其中记录的编码为准，`.usth` 恒为 UTF-8，都不需要这一项。
- **网络路径一律拒绝**：UNC 路径（`\\server\share`）与设备路径（`\\?\`、`\\.\`），相对路径与绝对路径都检查，解析为实际的路径之后再检查一次，因为相对路径经 `..` 拼接后同样可能指向网络位置。理由见下文「安全」。盘符映射到网络位置时不自动读取，经用户在明确的提示中同意后再读。**允许超出工程文件夹**，与 `$patch` 相同，因为被链接的文件只被读取，不被执行。

### 导出 `.ust` 与控制音符

**作者 2026-10-15 决定**：导出 `.ust` 时音符轨道即 UST 的正文，不在控制音符中再存一次。控制音符的载荷存放完整的 `tracks` 数组，顺序即显示的顺序，因此音符轨道的位置由它在数组中的下标表示，不另记下标。音符轨道一项只有 `type` 与名称、音量、声像、静音、独奏，不含 `voiceDir` 与 `notes`，两者取自 UST 的正文。音符轨道的名称与混音参数在 UST 的正文中没有对应的位置，因此放在这一项中，各项的写法与 `.usth` 相同，读写共用一套代码。

```json
"tracks": [
  {"type": "clips", "name": "伴奏", "clips": [
    {"type": "audio", "path": {"relative": "../bgm/inst.wav", "absolute": "D:/songs/bgm/inst.wav"},
     "start": 0, "clipStart": 0, "clipLength": 0}
  ]},
  {"type": "notes", "name": "主唱"}
]
```

载荷的未知字段原样保留（[`UsthFormat.md`](UsthFormat.md)「控制音符」），因此旧版本读写这样的 `.ust` 时轨道不丢失。一条轨道约百余字节，载荷的长度没有实际上限（实测 65536 个字符被原样保留，见同一节）。

以下为实现上的建议，未经作者决定：

- 没有音符轨道的工程不能导出 `.ust`。

### 互相链接

合唱时最常见的用法是 A 链接 B、B 也链接 A，各自对照对方的声部写和声。上文「只使用被链接工程的人声，不跟随其链接」的规则使互链自然成立：A 取 B 自己的人声，B 取 A 自己的人声，不形成循环，不需要额外处理。几个声部的情况相同，每份工程链接其余各份。

### 被链接工程的声音

有两种做法（写于作者的决定之前，当时假定 A 不执行 B 的合成工具）：

- **甲：B 写出人声文件。** B 渲染完成后，把自己那条轨道的混音写成一个文件，旁边记录 B 的工程文件的大小与修改时间。A 读取该文件，B 的工程文件比记录新时，照常播放旧结果并标出「须在 B 中重新渲染」。实现简单，但多出一类须管理的文件，B 只在实时方式下编辑而从未整轨渲染时也没有这个文件。
- **乙：A 从 B 的渲染缓存直接拼接。** A 读取 B 的工程与音源（只读），求出 B 的合成计划，按片段名从 B 的缓存目录取片段，以实时方式的拼接在本进程中混音。片段名是全部重采样参数、样本状态与重采样器的摘要（[`Synth.md`](Synth.md)「缓存」），因此过期的判断不需要另行设计：B 修改了哪个音符，A 就找不到哪个片段，该处显示为须在 B 中渲染。B 在实时方式下边编辑边渲染时，A 几乎同时得到新的声音。代价是 A 须读取 B 的音源，且结果取决于实时方式的拼接与 wavtool 的一致性（[`Synth.md`](Synth.md)「与 wavtool 的一致性」）。

建议采用乙。它复用现有的计划、缓存与拼接，不新增文件，下一节的「渲染结果的存放」与「以什么为键判断过期」两问随之解决。

**作者 2026-10-15 决定**：链接片段与音频片段地位相同，只是须经渲染。A 按渲染一份独立工程的方式渲染 B，使用 B 自己的设置、合成工具与缓存，与 B 在自己的窗口中渲染相同，不为链接另设「只补缺少的片段」之类的逻辑。B 的合成工具不受信任时（既不是本地设置中的合成工具，也未经用户信任），A 与渲染自己的工程时一样询问用户是否信任。用户不信任时，该片段不渲染，播放时无声。此前「由 A 只补渲染缺少的片段」的建议不采用，理由是它无端引入了 A 与 B 之间的耦合。

**沿用本工程的合成工具**（作者 2026-10-15 决定）：链接片段有布尔字段 `usesHostSynthTools`，缺省为 `false`。

- `false` 时按上文以 B 自己的合成工具渲染，结果写入 B 的缓存。
- `true` 时以 A 的 `Tool1`、`Tool2` 渲染 B，结果写入 A 的缓存。片段名包含重采样器，以 A 的工具渲染的片段与 B 自己的片段不通用，写入 B 的缓存只会留下 B 用不到的文件。A 的合成工具在 A 渲染时已经受信任，不再询问。
- 缺省为 `false`，因为 B 的作者是按 B 的重采样器调整的。同一组 flags 在不同的重采样器中含义不同，有的不被识别，默认改用 A 的工具会使 B 在 A 中的声音与在 B 中的不同，而用户无从得知原因。改用另一个重采样器还可能在 B 的音源文件夹中生成另一种格式的频率表与分析缓存。这也与「链接片段以被链接的工程为准」的原则一致。
- 这一字段的用途是 B 记录的合成工具在本机不存在，或用户不愿信任它们时，仍能听到 B。询问是否信任 B 的合成工具时，提示中另给「改用本工程的合成工具」一项，选择它即把该片段的 `usesHostSynthTools` 设为 `true`。

### 曲速

**作者 2026-10-15 决定**：链接片段的曲速以被链接的工程为准。在 A 中，链接片段的地位与音频片段没有区别，只是其声音须经渲染。A 的曲速只决定片段从哪里开始，片段的内容按 B 自己的曲速播放，与音频片段的内容按音频原样播放相同。因此不比较 A 与 B 的曲速，也不提供在两者之间复制曲速。此前「标出曲速不同的区段」与「从链接工程复制曲速」两条建议不采用。

- 起点默认为 0，即 A 与 B 同时开始。

### 安全

上文建议链接的文件像 `$patch` 一样可以在工程目录之外，因为它们只被读取、不被执行。网络路径须另作规定，理由比 `$patch` 更具体：在 Windows 上，读取 `\\server\share\...` 时系统会自动以当前用户的凭据向该服务器认证，一份构造的工程只要链接这样的路径，打开即可能向他人的服务器送出用户的认证信息。建议：

- 拒绝 UNC 路径（`\\server\share`）与设备路径（`\\?\`、`\\.\`），相对路径与绝对路径都检查，解析之后再检查一次。
- 盘符映射到网络位置时（`GetDriveType()` 返回 `DRIVE_REMOTE`）不自动读取，在明确的提示中经用户同意后再读。
- 被链接的 `.usth` 与 `.ust` 本身同样是不可信输入，按现有的读取路径解析，不因为「只是链接」而放宽。

### 实施顺序

1. **音频片段**：起点、音量、静音，随播放混音，导出时混入。只涉及解码与混音，不牵涉另一份工程，可以先交付伴奏的用法。混音器已支持并发的声源，见 [`Status.md`](Status.md)。
2. **链接片段的音符**：以只读的淡色显示 B 的音符，双击在新窗口中打开 B，B 保存后刷新。
3. **链接片段的声音**：按上文的乙。
4. **导出音频的三种方式**：混音、只导出 A 的人声、分轨导出。
