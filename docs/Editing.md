# 编辑层 `HelloKitEdit`

本文档规定编辑层的职责边界与接口结构。编辑层由两个目标组成：通用部分 `HelloKitEditBase`（`hellokit/lib/EditBase/`，include 路径 `<hellokit/EditBase/...>`，命名空间 `hello::kit::edit`）与文档部分 `HelloKitEdit`（`hellokit/lib/Edit/`，include 路径 `<hellokit/Edit/...>`，命名空间 `hello::kit`），见「通用层与文档层」。依赖 `HelloKitDocument` 与 `HelloKitVoiceBank`，节点树由 [substate](https://github.com/stdware/substate) 实现，作为私有依赖，见「节点树的实现」。

在 [`Roadmap.md`](Roadmap.md) 中，这是第三阶段「编辑器骨架」的**第一步**，先于窗口和钢琴卷帘。

## 概要

**编辑作用于一棵节点树。修改树的唯一途径是调用会话上的一组类型化函数，由这些函数自行记录变更，因此撤销、日志和通知都不是事后补充的。渲染和保存时，从树物化出一个 `Project`。命令是这组函数的文本接口。**

## 优先实现的理由

若在界面完成后再补充撤销栈，撤销栈就始终是补充的：总有一些入口绕过它，而这些入口恰恰产生最难复现的缺陷。反之，先确定「修改」的机制，界面就只负责将鼠标操作转换为函数调用。

另一项直接收益是：**编辑语义在没有界面时即可测试**。

## 职责边界

| | 归属 |
|---|---|
| 文件格式与读写 | `HelloKitDocument` / `HelloKitVoiceBank` |
| 编辑、撤销、崩溃恢复 | **`HelloKitEdit`** |
| 修改后的发声 | `HelloKitSynth` |
| 鼠标操作到修改的转换 | `HelloUtauEditor` |

`HelloKitEdit` 不依赖界面，不链接 QtWidgets。

## 事实来源：节点树

编辑期间，**树就是文档**。`Project` 和 `VoiceBank` 仍是普通的值类型，负责读写文件和向合成层提供数据，但它们是**从树物化出的快照**，而非被编辑的对象。

```
                    ┌──────────────┐
   .ust / .usth ───▶│              │───▶ Project ───▶ SynthPlan
                    │     树       │      （快照）
   界面 / 命令  ◀──▶│  （会话独占） │───▶ Project ───▶ 保存
                    └──────────────┘
```

**规则：界面读取树，合成读取快照。** 渲染本就应当基于快照进行：一次渲染需要数秒，期间用户仍在编辑，读取快照是正确的做法。

### 代价与取舍

代价是**两份表示**，二者之间的转换是新的偏差来源。防范手段是往返测试，而这种结构已有成熟的先例：`.usth` 与 `Project` 之间的转换即以此方式保证，`ustconv --check` 的判据可以直接复用。

换来的是节点模型的全部优势：身份、属性与子节点的统一，以及自然的嵌套寻址。**即使不采用树，这些功能也必须自行实现一遍**，那才是代价最高的方案。

现有代码**无需任何改动**：222 处 `Note` 字段访问、两个读写器、`SynthPlan::make(const Project &)`、MIDI 转换、所有手动工具和测试均保持不变。新增的只有树的定义和一层双向转换。

## 节点模型

使用 substate 的三种节点，外加「槽位内容」的概念：

| 节点 | 语义 |
|---|---|
| `StructNode` | **固定槽位**的记录。槽位表在编译期确定，按下标寻址 |
| `VectorNode` | **有序**的子节点列表，按下标执行 `insert` / `remove` / `move` |
| `MappingNode` | 键到值的映射 |

槽位内容即 qsubstate 的 `Property`：为空、一个 `QVariant` 标量，或一个子节点。

**`Property` 将「属性」和「子节点」统一为同一种槽位机制。** 因此「修改一个标量」和「替换一个子节点」是同一种操作，变更记录只有一种形式。`pitchBend` 是否为 `null`，即对应槽位中是子节点还是为空。

substate 另有 `SheetNode`（键由节点分配的表）、`BytesNode` 与 `ArrayNode<T>`（按元素下标访问的数值数组）。元素需要身份时使用节点，数量大且只作为数值序列整体编辑时使用 `ArrayNode<T>`，选择标准见 substate 的 `docs/Design.md`「节点与数组的选择」。

### 身份

每个节点有一个在会话内稳定的 `NodeId`：插入、删除、撤销、重做都不改变已存在节点的 ID。

**界面使用 ID，寻址使用下标。** 正在拖动的音符、选中的控制点，记录的是 ID；`/tracks/0/notes/12` 这样的路径供命令和日志使用。下标会随插入和删除而变化，ID 不会。

ID **不保存到文件**。打开文件时重新生成，因为它是会话内的引用，而非文档内容。

## 模型到节点树的映射

| 模型类型 | 节点 | |
|---|---|---|
| `Project` | Struct | settings / tracks / unknownFields |
| `ProjectSettings` | Struct | 全部为标量槽位 |
| `tracks` | Vector | 长度恒为 1 |
| `Track` | Struct | name / voiceDir / notes |
| `notes` | **Vector** | 见下文 |
| `Note` | Struct | 标量槽位与子节点槽位（portamento / pitchBend / userData）。envelope 与 vibrato 各为一个整体值，修改其中一项即替换整个值 |
| `pitchBend` | Struct | start / values，values 为 `ArrayNode<double>` |
| `portamento` | Vector | 控制点有序 |
| `PortamentoPoint` | Struct | x / y / type |
| `userData` / `unknownFields` | Mapping | 键为 UST 中的名称 |
| `VoiceBank` | Struct | character / prefixMap / readme / directories。前三项取自根目录 |
| `character` | Struct，可为空 | `character.txt` 的各项与其余行 |
| `prefixMap` | Mapping，可为空 | 键为音高的十进制写法，值为前缀与后缀，整体一个值。为空表示没有 `prefix.map`，与没有条目的空文件不同，命令不能在空的槽位上设置键 |
| `directories` | Vector，只读 | 读取到的全部目录，根目录在前，按读取顺序。目录只随从磁盘重新读取而增减 |
| 目录 | Struct | path / charset，均为只读；otoEntries。path 以斜杠分隔；编码由「转换编码」的领域函数修改。未能读取的目录不在树中 |
| `otoEntries` | Vector | `oto.ini` 的条目，按文件名的字节排序，同一 wav 的条目按文件中的顺序，与保存时的顺序相同。一个 wav 可有多个条目 |
| oto 条目 | Struct | fileName / alias / 五个时间参数，以及五个数字的原有写法（不公开）。没有条目的 wav 不在树中，由磁盘状态记录的音频文件减去条目引用的文件得到 |

### 音符采用 Vector 的理由

音符采用有序列表，而非带起始位置的集合，**因为休止符不是空白。** UST 中的休止符可以携带 `Tempo`（变速点即位于休止符上）、`Label` 以及以 `$` 开头的自定义条目。将休止符视为「空隙」会丢失这些内容，直接违反 UST 往返语义一致的保证。

顺序即时间，与 UST 的存储形式一一对应，保存时无需转换。代价是「将音符后移 100 tick」不是修改一个字段，而需要调整相邻休止符的长度。这属于界面层的职责，封装为一个领域函数即可；而丢失数据则无法接受。

`VectorNode` 的元素仍各自带有 ID，因此**有序与身份并不冲突**。

## 三个层次

```
命令（文本）        note set 0 12 lyric a
      │            仅为接口，没有独有的能力
      ▼
领域函数            transpose / quantize / insertNotes / splitNote …
      │            数量多；组合下一层；每次调用包含在一个事务中
      ▼
节点操作            set 槽位 / insert / remove / move
                   数量少，类型化，**变更记录在此层进行**
```

### 节点操作：数量少且类型化

槽位不是裸下标。schema 将每个槽位声明为一个带类型的句柄：

```cpp
namespace NoteSlots {
    inline constexpr Slot<QString>               Lyric{0, "lyric"};
    inline constexpr Slot<int>                   Length{1, "length", Range<int>::atLeast(1)};
    inline constexpr Slot<int>                   NoteNum{2, "noteNum", Range<int>::between(0, 127)};
    inline constexpr Slot<std::optional<double>> Intensity{3, "intensity"};
    // …
}
```

槽位表同时承担类型、名称（供日志和命令层使用）和约束（见下文）三项职责。范围的类型即槽位值的类型（可空的槽位去掉 `std::optional`），整数槽位的边界是整数；字符串、布尔、枚举与整体值的槽位不接受范围，写了即编译失败。

### 句柄：节点操作的公开接口

界面代码通过句柄（`ProjectRefs.h`）读写树。句柄是值类型，内含会话指针与 `NodeId`，按文档的概念命名：音符、控制点、音高曲线，而非记录、列表、映射。每个成员函数在库内直接对一个 substate 节点执行一种变更形状，公开头文件只有声明，因此不出现 `ss::` 类型：

```cpp
ProjectSession session(project);
const auto notes = ProjectRef(&session).tracks().at(0).notes();
const auto note = notes.at(12);
note.setLyric(QStringLiteral("a"));             // 写入 NoteSlots::Lyric
note.setIntensity(std::nullopt);
notes.insert(13, {newNote});                    // 插入 Note 值的副本
note.userData().remove(QStringLiteral("$Custom"));
```

类型由句柄的函数签名保证，`note.setNoteNum(QStringLiteral("abc"))` 无法编译。

句柄可以复制和保存。节点被删除后句柄无效（`isValid()` 为假），撤销删除后重新有效，因为 ID 不变。句柄不带信号，也不记录变更：变更由 substate 的动作记录，通知由会话统一发出，见「变更通知」。

**不设公开的「按节点种类」访问层。** 界面不需要以「记录的第几个槽位」「列表的第几项」的方式访问树，按种类逐一包装 substate 的节点接口只会重复它，substate 每增加一种节点就要再包装一次。命令层需要的按槽位名寻址在库内部实现。

### 变更通知

会话只有两个信号：`changed(ChangePtr)` 与 `stepChanged(int)`。后者给出撤销历史中的绝对步数 `currentStep()`，界面据此判断文档是否与保存时相同：当前步数等于保存时的步数，即未修改。`Change` 是多态的值：基类只含种类编号与节点 ID，数据由子类携带，接收方以 `as<T>()` 区分：

| 子类 | 数据 | 对应的动作 |
|---|---|---|
| `ValueChange` | 槽位下标 | 槽位赋值，包括替换或移除子节点 |
| `EntryChange` | 键 | 映射项增删改 |
| `ArrayChange` | 无 | 数组的插入、删除、覆盖 |
| `ListChange` | 类型（插入、即将删除、已删除）、下标、数量 | 序列插入与删除 |
| `MoveChange` | 下标、数量、目标位置 | 序列移动 |

所有变更按发生顺序出现在同一条流中，撤销、重做与回滚同样按实际方向报告。变更不含指向树的指针，可以排队传递和保存，因此也是变更日志的来源。

**拖动等持续的操作在进行中不修改树，结束时以一个事务写入最终结果。** 操作进行中的变化只是视图内的临时显示，不是对文档的修改。撤销步骤因此只含实际的修改，不会因为一次拖动而记录上百次赋值，变更流与变更日志也只出现最终结果。会话不提供按事务合并的通知：一个事务中确有多条变更时，需要成批处理的接收方（卷帘的重绘、合成缓存的失效）在 `changed` 中只作标记，稍后统一处理。

**新增节点种类时，会话核心不需要修改。** substate 动作到变更的翻译按动作类型注册在扩展接口中，内置的几种节点也经由同一机制注册。新节点种类提供自己的句柄、自己的 `Change` 子类（种类编号从 `Change::User` 起）、翻译函数和变更日志的写法（`registerLogWriter`），内置的五种变更的日志写法同样经由这一接口注册。

**翻译函数与变更的接收方不得抛出异常。** 翻译函数在 substate 执行、撤销、重做每个动作的通知中调用，而 substate 的撤销与重做不处理中途的异常：已应用的动作不回退，步数已经改变，模型停在撤销或重做的状态，之后无法再使用。撤销与重做只修改内存中的树，不涉及磁盘，执行动作本身不会失败，因此这一约束足以保证撤销与重做完整进行。

### 领域函数：数量多，组合节点操作

`insertNotes`、`splitNote`、`transpose`、`quantize`、`setTempoAt`、`normalizeEnvelopes` 等，数量不设上限，因为它们是产品功能。每个领域函数将若干节点操作包含在**一个事务**中，因此构成**一个撤销步骤**。

领域函数不自行记录变更，其调用的节点操作已经记录。

领域函数是 `ProjectEdits` 的静态函数（`ProjectEdits.h`），只使用公开的句柄。每个函数返回事务是否提交，未提交的原因写入 `DiagnosticList`。在另一个事务中调用时加入该事务，因此组合出的操作仍是一个撤销步骤。第一批：

| 函数 | 语义 |
|---|---|
| `transpose` | 给定音符的 `noteNum` 各加一个半音数，休止符同样移调 |
| `splitNote` | 在音符内部的某个 tick 处拆分。原音符保留全部字段并缩短，其后插入一个新音符：剩余长度、相同的 `noteNum`、默认歌词，不带其他字段 |
| `insertNotes` | 在某个音符之前或最后一个音符之后按顺序插入若干音符，其后的音符整体后移，不切分任何音符；各字段原样写入，包括速度。用于插入音符、画笔与 [`Tuning.md`](Tuning.md) 第 6 步的粘贴 |
| `setTempo` | 写入音符的速度，即使与该处已生效的速度相同也写入。速度从该音符起生效，直至下一个带速度的音符，后续音符的生效速度是由此推导的状态，不写入工程 |
| `removeNotes` | 删除给定下标的音符（顺序任意），其后的音符前移。被删除音符的全部字段随之删除，包括速度，因此其前生效的速度延续下去 |
| `setLength` | 设定一个音符的长度，其后的音符随之前移或后移 |
| `moveNotes` | 把一段连续的音符在序列中移到另一位置，不改变任何长度，轨道总长不变；各字段随音符移动，包括速度。语义见 [`Widgets.md`](Widgets.md) 第 4 步 |
| `setPortamento` | 替换一个音符的 Mode2 控制点，只写入有差别的点，其余的点保留其节点；多出的点从末尾删除，新增的点追加在末尾。控制点须保持顺序（自第二点起不早于前一点）。用于 [`Tuning.md`](Tuning.md) 第 2 步 |
| `setVibrato` | 把若干音符的颤音设为同一值，或全部去掉。用于 [`Tuning.md`](Tuning.md) 第 3 步 |
| `setEnvelope` | 把若干音符的包络设为同一值，或全部去掉（即 UTAU 的默认包络）。用于 [`Tuning.md`](Tuning.md) 第 4 步 |
| `scalePitch` | 把若干音符各控制点的高度乘以一个倍数、颤音深度乘以另一个倍数，取整到音分；倍数不得为负。用于 [`Tuning.md`](Tuning.md) 第 6 步 |
| `setParameter` | 把若干音符的力度、调制或速度（`NoteParameter`）设为同一值，或全部去掉（即 UTAU 的默认值）。用于 [`Tuning.md`](Tuning.md) 第 7 步 |
| `drawPitchBend` | 把一串值画进一个音符的 Mode1 值：第一个值在距音符起点若干 tick 处，其后每 5 tick 一个，按该音符的速度换算（`PitchBend::drawn()`）。没有值的音符从该处开始（`PBStart` 取到千分之一毫秒）；已有值的音符保持起点，位置取最近的格点，值向前或向后延伸，画出的值与原有的值之间按原来的曲线补齐（取整），使没画到的地方听起来不变。用于 [`Tuning.md`](Tuning.md) 第 5 步 |
| `setPitchBend` | 以给定的值整体替换一个音符的 Mode1 值，空值即删除；与原值相同时不产生步骤。用于「Convert Mode2 Pitch to Mode1」（[`Tuning.md`](Tuning.md)） |
| `setLabel` | 设置一个音符的标签（UST 的 `Label`），空文字即删除 |
| `nameRegion` | 为一段连续的音符命名区间：第一个音符的 `regions` 与最后一个音符的 `regionEnds`（UST 的 `$region` 与 `$region_end`）各加入区间名；多个区间共用同一端点时各占数组的一项，两端已有的其他区间名保留；空名与含 `|` 的名称拒绝（UST 以 `|` 分隔名称）；范围为空或超出音符时拒绝 |
| `renameRegion` | 把一个区间（`Region`：名称、首音符、末音符，由 `Track::regions()` 或 `NoteListRef::regions()` 解析）改名：在首音符的 `regions` 与末音符的 `regionEnds` 中原位替换，未结束的区间只改首音符；两端其他区间的名称保留。区间不存在、新名称为空或含 `|`、新名称已是同一端点上另一区间的名称时拒绝（作者 2026-10-08 决定，审查清单 P0-8） |
| `removeRegion` | 删除一个区间：从首音符的 `regions` 与末音符的 `regionEnds` 中只删去它的名称，同一端点上其他区间的名称保留；区间不存在时拒绝 |
| `setMode2` | 打开或关闭工程的 Mode2，即合成用控制点与颤音还是用 Mode1 值；另一种数据保留。用于 [`Tuning.md`](Tuning.md) 第 5 步 |
| `combineNotes` | 把一段连续的音符合并到第一个音符（同 UTAU 的「音符合并」）：长度为它们之和，其他属性取第一个音符的，一个撤销步骤「Combine Notes」。少于两个音符时拒绝；第一个之后的音符设了曲速时拒绝，因为合并会丢掉这个曲速，其后所有音符的时刻都会改变（作者 2026-09-29 要求） |
| `setNoteProperties` | 改音符的属性（`NotePropertyChanges`）：歌词、长度、曲速、力度、调制、辅音速度、先行发声、重叠、STP、flags，只改给出的字段，对每个音符相同，一个撤销步骤「Change Note Properties」；能留给默认值的字段设为空即清除。用于音符属性对话框与曲速（作者 2026-09-29 要求） |
| `setProperties` | 改工程的属性（`ProjectPropertyChanges`）：名称、速度、flags、输出文件、第一条音轨的音源目录、两个合成工具、Mode2，只改给出的字段，一个撤销步骤「Change Project Properties」；没有任何变化时不产生步骤。两个合成工具只记录，不执行。用于工程属性对话框（作者 2026-09-29 要求） |

卷帘的「Remove Label」是界面操作，不新增领域函数：对选中的音符分别调用 `setLabel` 清空标签，在外层合并为一个事务，因此占一个撤销步骤。「Remove Region」调用 `removeRegion` 删除第一个选中音符所在的区间。

## 六种变更形状

变更记录是通用的，按形状各实现一次，而非每个函数各实现一次。每种形状对应 substate 的一种动作：

| 形状 | 记录内容 | 逆操作 |
|---|---|---|
| 槽位赋值 | 修改前后的值 | 写回修改前的值 |
| 序列插入 | 区间 | 删除该区间 |
| 序列删除 | 被删除的子树 | 重新插入 |
| 序列移动 | 区间与目标位置 | 反向移动 |
| 映射项增删改 | 键、修改前后的值 | 写回修改前的值 |
| 转移 | 源父节点与位置、目标父节点与位置 | 转回源位置 |

**转移**把节点移到另一个父节点下，节点的身份与 ID 不变，例如将来的多轨工程中把音符移到另一轨。以删除后插入副本代替转移，会使界面中以 ID 记录的选区与拖动状态失效。目前没有领域函数使用转移，会话也尚未为转移动作注册到变更的翻译；首次使用转移时须一并补上，否则执行时触发断言。

**若某个操作无法归入这六种形状，不应急于添加第七种，更可能的是该操作应当拆分。**

## 事务

```cpp
{
    auto tx = session.transaction(tr("移动 3 个音符"));
    notes.move(12, 3, 20);
    if (!ok) {
        return;         // 未提交，析构时回滚
    }
    tx.commit();
}
```

**提交必须显式调用 `commit()`，未提交的事务在析构时回滚。** 析构函数无法区分正常到达作用域末尾与中途返回，若析构即提交，提前返回也会留下修改。回滚发出的通知与撤销相同，界面据此还原。`commit()` 返回是否提交，未提交的原因写入 `DiagnosticList`。

**事务可以嵌套。** 领域函数各自开启事务，因此单独调用时构成一个撤销步骤；被另一个领域函数调用时，其事务嵌套在外层事务中，由最外层事务构成撤销步骤并使用最外层的消息。substate 不支持嵌套，会话在自身一层计数，只有最外层事务调用 substate 的 `beginTransaction()`。内层事务未提交即结束时，整个事务作废：已执行的修改保留到最外层事务结束，届时整体回滚，最外层的 `commit()` 返回 `false` 并给出原因。

事务消息即界面上「撤销：移动 3 个音符」中的文字，也是无界面模式日志中输出的内容。

## 校验的两个位置

**属性级约束（范围、格式、枚举）声明在槽位表中**，例如 `Slot<int> NoteNum{2, "noteNum", Range<int>::between(0, 127)}`。一处定义，提交时的校验和命令层共用；命令层还据此生成帮助文本并校验参数。约束随字段声明，添加字段时不会遗漏。setter 不检查属性级约束，它们与跨字段的约束一同在提交时检查。

**跨字段、跨节点的不变量在事务边界处检查**，而非在函数内检查。包络锚点的顺序、portamento 的 x 值递增、同一 wav 下 oto 别名不重复，这类约束**在中间状态下可以合理地不满足**：一次「将三个音符后移」由先删除后插入组成，删除完成时的状态无法通过检查，逐函数校验会产生误报。

因此参照数据库的做法：**约束延迟到提交时检查**。事务内允许中间状态，提交前对受影响的记录执行校验，不通过则整体回滚，`commit()` 返回 `false` 并在诊断中列出违例。RAII 事务本就需要在异常和提前返回时回滚，二者使用同一条路径。

**只拒绝事务新引入的违例。** 读取外部 UST 时会遇到越界值，打开文件不因此失败，修改同一记录的其他字段也不应因此失败。事务第一次修改一个记录之前，会话先对它执行一次校验，记下已有的违例；提交时再校验，只有出现了原来没有的违例才回滚。事务插入的记录没有修改前的状态，其全部违例都视为新引入。事务删除的记录不再校验。

**受影响的记录**由变更得出：从变化的节点沿父节点向上，第一个注册了校验的记录。例如修改 portamento 控制点的 x 时，受影响的是持有该列表的音符，其校验检查各点之间的关系。校验由文档层按节点类型经扩展接口注册，属性级约束的检查可由槽位表生成，跨字段的约束手写。

工程目前的约束：

| 记录 | 约束 |
|---|---|
| 工程 | 轨道恰为一条 |
| 设置 | 速度大于 0 |
| 音符 | 长度至少为 1；`noteNum` 在 0 到 127 之间；速度（若有）大于 0；包络各锚点与前一锚点的间距不为负；portamento 第二个点起与前一点的间距不为负，第一个点相对音符起点，可以为负 |

**读自文件的内容不校验。** 文档层以磁盘上的内容替换文档的一部分时（例如从磁盘重新读取音源的一个目录），把该事务标记为读自文件，提交时不校验，与打开文件时不校验一致。否则磁盘上本就存在的违例会被当作新引入，重新读取就会失败。

另有第三种方式值得一提但目前不采用：**使非法状态无法表示**（例如 `noteNum` 使用带范围约束的类型）。这是最严格的方式，但读取外部 UST 时确实会遇到越界值，读取层必须能容纳非法值并报告诊断，类型一旦收紧，这条路径即被阻断。

## 命令

每行一条，每条对应**一个事务**，事务消息即命令原文，因此一条命令是一个撤销步骤。命令被拒绝时事务回滚，文档不变。命令分两类：

```
set     /tracks/0/notes/12/lyric "a i"
insert  /tracks/0/notes/12/portamento 2 {"x": 20, "y": 0, "type": "R"}
remove  /tracks/0/notes 12 3
note transpose 2 /tracks/0/notes/12 /tracks/0/notes/13
note insert /tracks/0/notes 12 {"lyric": "a", "length": 480, "noteNum": 60}
```

**节点操作**（`NodeCommands_p.h`，通用层）按路径寻址，覆盖句柄的全部操作。路径所指的字段种类决定可用的命令：

| 命令 | 字段种类 | 作用 |
|---|---|---|
| `set <路径> <值>` | 值 | 写入。可空的字段写 `null` |
| `set <路径> <对象\|null>` | 可空的记录 | 整体设置或移除 |
| `set <路径> <键> <值>` / `remove <路径> <键>` | 映射 | 写入或移除一项，键是参数而非路径的一段 |
| `insert <路径> <下标> <对象>…` | 列表 | 由 JSON 创建记录并插入 |
| `remove <路径> <下标> [<数量>]` | 列表、数组 | 删除，数量默认为 1 |
| `move <路径> <下标> <数量> <目标位置>` | 列表 | 目标位置是移动后第一项的下标 |
| `insert` / `replace <路径> <下标> <数值>…` | 数组 | 插入或覆盖，覆盖可越过末尾 |

**领域命令**（`ProjectCommands.h`）每个领域函数一条，形式为 `<名词> <动词> [参数…]`：`note transpose <半音数> <音符路径>…`、`note split <音符列表路径> <下标> <tick>`、`note insert <音符列表路径> <下标> <音符>…`、`note tempo <音符路径> <速度>`、`note remove <音符列表路径> <下标>…`、`note length <音符路径> <tick>`、`note move <音符列表路径> <下标> <个数> <目标下标>`、`note portamento <音符路径> <控制点数组>`、`note vibrato <颤音或 null> <音符路径>…`、`note envelope <包络或 null> <音符路径>…`、`note scale <控制点倍数> <颤音倍数> <音符路径>…`、`note parameter <intensity、modulation 或 velocity> <值或 null> <音符路径>…`、`note bend <音符列表路径> <下标> <tick> <值数组>`、`note pitchbend <Mode1 值或 null> <音符路径>`（对象的键为 `start`、`values`）、`note combine <音符列表路径> <下标> <个数>`、`note label <文字> <音符路径>`、`note region <音符列表路径> <下标> <个数> <名称>`、`note renameregion <音符列表路径> <首音符> <末音符> <名称> <新名称>`、`note removeregion <音符列表路径> <首音符> <末音符> <名称>`、`note properties <对象> <音符路径>…`（键为 `lyric`、`length`、`tempo`、`intensity`、`modulation`、`velocity`、`preUtterance`、`voiceOverlap`、`startPoint`、`flags`，数值键可为 `null` 表示清除）、`settings mode2 <true 或 false>`、`settings properties <对象>`（键为 `name`、`tempo`、`flags`、`outputFile`、`voiceDir`、`wavtool`、`resampler`、`mode2`，只含要改的键）。音源的领域命令（`VoiceBankCommands.h`）：`entry set <条目路径> <条目>`、`entry insert <目录路径> <条目>…`、`entry include <目录路径> <文件名>…`、`entry remove <目录路径> <下标>…`、`prefix set <音高> <前缀>`、`prefix remove <音高>`、`character set <character.txt 的对象>`、`readme set <文本>`、`directory charset <目录路径> <编码名>`、`directory fileNameEncoding <目录路径> <文件名编码的记录或 null>`（记录的形式与 `hello-config.json` 相同）。插入的条目按文件名排入，不由命令指定位置。

**查询只读取文档，不修改文档。** 目前只有一个：`get <路径>`，返回路径所指内容的 JSON，写法与命令的参数、变更日志相同：记录按其文档的写法（如音符、oto 条目），文档未定义写法的记录（如工程的根、音源的目录）写成各字段组成的对象；列表是数组，项在数组中的位置就是命令所用的下标；映射是对象，数组是数字的数组；空的值、缺席的记录或映射写作 `null`。不公开的字段既不能寻址，也不输出。查询不开事务，不产生撤销步骤，由 `ProjectCommands::query()` 与 `VoiceBankCommands::query()` 执行；交给 `execute()` 时被拒绝。例如 `entry remove` 所需的下标由 `get /directories/1/otoEntries` 查得。

**命令只写入它所写明的值。** 读取文件时宽容的地方，命令一律拒绝：记录与整体值中的未知字段、类型不符的字段，以及读取时会被修正为默认值的写法，都报告错误而不写入。音高只接受数字，不接受音名。

参数以空白分隔，**转义只有一套，即 JSON 的规则**（`CommandSyntax.h`）。参数有四种形式：

| 形式 | 识别方式 | 例子 |
|---|---|---|
| 裸词 | 不以 `"`、`@"`、`{`、`[` 开头，到空白为止，其中不含 `"` | `12`、`lyric`、`null`、`a` |
| 字符串 | 以 `"` 开头的 JSON 字符串，使用 JSON 的全部转义 | `"a i"`、`"say \"hi\""`、`"line\nbreak"` |
| 原样字符串 | 以 `@"` 开头，到未成对的 `"` 为止。没有转义，两个 `"` 表示一个 | `@"C:\tools\resampler.exe"`、`@"say ""hi"""` |
| 结构值 | 以 `{` 或 `[` 开头的 JSON 对象或数组，读到匹配的括号为止，中间可有空白 | `{"period": 180, "length": 65}` |

**参数的值不取决于接收它的字段。** 裸词若是 JSON 的数字、`true`、`false` 或 `null`，即为该值，否则为其文字；字符串和原样字符串总是文字。因此歌词 `12` 须写为 `"12"`，写成裸词是数字，交给字符串字段时报告类型错误，不做转换。数字按 JSON 的语法判断，`012`、`.5` 不是数字。原样字符串取自 C# 的逐字字符串，用于含反斜杠的路径和 flags。

字符串与结构值的边界由分词器找出，内容交给 JSON 解析器，不另写转义代码。结构值的写法即 `.usth` 中该字段的写法，可直接从工程文件复制，变更日志中的值也使用同样的 JSON 写法。Qt 的 JSON 解析器接受反斜杠后的任意字符，JSON 并不允许，因此分词器只接受 JSON 规定的转义。不支持单引号、反引号和变量展开。空行和以 `#` 开头的行不含命令。

### 路径寻址

嵌套较深时使用路径更为方便：

```
set /tracks/0/notes/12/vibrato/period 180
set /tracks/0/notes/12/intensity null
```

以 `/` 分隔，每段为槽位名或十进制下标，`/` 本身表示根。路径到达值字段后可以继续，各段为该值 JSON 写法中的成员，如上例的 `vibrato/period`、`envelope/anchors/1/y`：修改一个成员即整体替换该值，成员必须已存在，新值的 JSON 类型须与原值相同。**路径中永远不出现数据**：歌词、flags、文件名只作为*值*出现。因此路径无需转义，也不会因歌词中含有空格或斜杠而解析错误。

`std::optional` 类型的字段以 `null` 表示「文件未指定」。`set …/intensity null` 与 `set …/intensity 100` 含义不同，在 UST 中同样不同。

### 变更日志：JSON Lines

供程序读取的日志采用 JSON Lines，其转义规则现成，可容纳任意字符，插件和外部工具也易于生成：

```json
{"after":"i","before":"a","node":41,"shape":"set","slot":"lyric"}
{"after":"v","key":"$Custom","node":52,"shape":"entry"}
{"count":1,"index":12,"node":17,"shape":"insert"}
```

每个 `Change` 一行（`ProjectSession::logEntry()`），`shape` 为 `set`、`entry`、`array`、`insert`、`remove`、`move` 之一，对应「变更通知」中的五种子类。`node` 是节点 ID，槽位以 `.usth` 的字段名表示，值按 `.usth` 的 JSON 写法。可空字段的空值写作 `null`，与命令相同；映射项不存在时省略 `before` 或 `after`，因为 `null` 是未知字段的合法值。整体替换的子记录只写出替换后的值，替换前的子记录已不在树中。删除只在执行后记录一次。撤销与重做按实际方向记录。

### 命令不是脚本语言

没有变量、条件、循环和表达式求值。需要这些功能时，应使用插件。

### 选区不进入命令层

参数始终显式给出。界面将「当前选中的音符」转换为显式参数后再发送命令。这样，一串命令的含义不依赖于执行时的选区状态，因此脚本可以重放，测试可以编写。

## 音源是第二种文档

音源从一开始就与工程一同设计。音源的结构与工程差别很大，这正是需要一同设计的原因：一个 wav 可以有**多个** oto 条目，一份音源可以有**多个目录，各自包含一份 `oto.ini`**，而且**各目录的编码可能不同**。

### 树的结构

**`character`、`prefixMap`、`readme` 属于整个音源，只取自根目录；只有 oto 按目录递归读取。** 映射见「模型到节点树的映射」。目录是 oto 的保存、编码与重新读取的单位，每个目录下是其 `oto.ini` 的条目。根目录的编码同时用于这三个文件。整个音源的样本列表（合并视图）由树推导，不单独存储。

- **读取任意深度的子目录中的 `oto.ini`。** UTAU 只读取根目录及其下一层子目录中的 `oto.ini`（依据：utau.exe 的反编译结果，读取 oto 的函数以 `Dir` 列出根目录的子目录，不递归；它对每个目录只读取 `oto.ini` 并列出 `*.wav` 与 `*.aiff`，不读取其他文件）。HelloUtau 读取任意深度，与 [`note.md`](note.md) 一致，不提示更深层目录中的条目在 UTAU 中不生效。
- **子目录中的 `character.txt`、`prefix.map` 与 `readme.txt` 不读取，也不写入。** UTAU 只从音源目录读取这三个文件（依据同上：读取函数只将传入的音源目录与文件名拼接一次）。子目录中的同名文件只在该子目录被单独选为音源时使用，与本音源无关，因此磁盘上的这些文件保持原样。现有代码为每个目录保留这三个文件，拆出账本时一并改为只取根目录；子目录是否需要选择编码，也随之只取决于其 `oto.ini`。
- **裸 wav 不进入树。** 没有 oto 条目的 wav 由扫描磁盘得到，与树中的条目对照即为「未收录的 wav」。用户同意收录时，为其插入条目，这是一次普通的编辑。
- **oto 一次读取全部。** 打开时读取并解码全部目录，树一次建立完整。别名查找表由快照建立，供合成使用；编辑期间另有一份由树建立、随变更通知更新的索引，供别名唯一性校验与搜索使用。
- **未能读取的子目录（`leftOut`）不进入树，视为不存在。** 这是用户没有为其选择编码的目录，不能保存，快照中也没有它及其中的样本。会话另外记下这些目录（`excludedDirectories()`），供界面提示用户选择编码重新读取；读取成功后，它作为一个新目录加入树。**根目录读不了时会话建立失败**，如同一个未能读取的文件打不开。真正使音源打不开的只有文件夹不存在或无权访问，以及根目录读不了这两种情况。
- **在所选编码下不合法的字节读作 U+FFFD，目录照常进入树。** 见「编码的选择与记录」。
- **`oto.ini` 不存在与内容为空在树中相同，都是没有条目**，UTAU 也不区分二者。区别由磁盘状态记录：保存时，不存在的 `oto.ini` 只在加入了条目后才创建，空的 `oto.ini` 未经修改则保持原样。

### 内容与磁盘账本分离

音源分三个类型，分别对应读盘、内容与磁盘状态：

| 类型 | 持有 | 性质 | 工程一侧的对应 |
|---|---|---|---|
| `VoiceBankSource` | 读盘的原始结果：各目录未解码的文件、文件摘要、目录指纹 | 一次读取的结果。编码未记录时，据其原始别名询问用户 | stdutau 的 `UstFile` |
| `VoiceBank` | 根目录、各目录的内容、样本、别名查找表 | 纯值，可复制 | `Project` |
| `VoiceBankFileSystemState` | 每个文件读取或写出时的修改时间、大小与摘要，`hello-config.json` 中本版本不认识的字段，目录指纹 | 会话持有，随保存与重新读取更新 | 无 |

工程没有对应磁盘状态的类型，因为保存 UST 即整体重写一个文件。音源的保存只写编辑碰过的文件、拒绝替换已被其他程序修改的文件，检查磁盘还要比较目录指纹，后两者须记住每个文件读取时的属性。

编辑期间内容以树为准。为了不在树之外再保存一份内容，**磁盘状态与内容分开，由会话持有**。二者按目录路径而非下标对应：内容中有而磁盘状态中没有的目录从未读取，保存时报告错误；磁盘状态中有而内容中没有的目录，保存时跳过。只读取音源的调用方（如合成）使用 `VoiceBank::open()`，不必持有磁盘状态。

打开时同时得到二者。保存时从树物化出 `VoiceBank` 快照，与账本以及要写入的文件一同交给保存函数。合成直接使用快照。音源因此与工程遵守同一条规则：**界面读取树，合成与保存读取快照。** `hello-config.json` 由保存写入而非由用户编辑。其中的编码与文件名记录进入树，只有本版本不认识的字段留在账本中。

### 读写的保证

以下各项由保存函数保证，编辑层无需处理：

- **只写入编辑碰过的文件**，由撤销历史决定，不比较内容，见「保存时写入哪些文件」。使用 LF 换行或未排序的文件，未经修改就不会被重写。
- **按各目录自身的编码写入。** 编码无法表示的字符被拒绝，**一次列出全部**，不写成 `?`。
- **含 U+FFFD 的文本不写出。** U+FFFD 代表读取时不合法的字节，写出即丢失原来的字节。修改过的文件中只要含有 U+FFFD，保存即失败，并一次列出全部位置；未修改的文件不重写，不受影响。
- **`oto.ini` 的编码声明只能是 UTF-8，声明决定整个目录的编码。** 首行 `#Charset:UTF-8` 或 `#Charset:UTF8`（不区分大小写）表示该目录的全部文本文件按 UTF-8 读写，优先于 `hello-config.json` 的记录，也不再询问。声明由编码推出：目录的编码为 UTF-8 时，`oto.ini` 写出时一律带上 `#Charset:UTF-8`，原本没有声明的补上；为其他编码时不带声明。声明其他编码的行视为不存在：目录的编码按记录或询问确定，重写时不再写出该行。
- **拒绝替换磁盘上已被其他程序修改的文件**（UTAU 的 setParam 可能同时运行）。全部检查通过后才开始写入，失败时不修改任何文件。判断方法与 `hello-config.json` 的例外见「保存时写入哪些文件」。
- **未能读取的目录（`leftOut`）不写入**，否则未读取的内容将被写为空。
- 目录的编码须记录时（打开时由用户选定，或经转换、重新解读而改变），下次保存将其写入 `hello-config.json`。未修改的目录不会多出文件。
- `hasEntry == false` 的样本（按文件名演唱的样本）不会写成一行条目。
- 数字保留原有写法（同一文件中 `41` 和 `41.0` 均可能出现，也有五个数字全空的条目）；修改过的数字按最短写法重写。
- `oto.ini` 保存时按文件名排序：条目按文件名归组，各组按文件名在该文件编码下的字节排列，同一文件名的条目保持读取时的先后。stdutau 读取时即以文件名为键保存条目，行序不予保留。**UTAU 保存时同样排序**，因此没有音源能指望其条目顺序在一次保存后保持不变。原本已按此顺序排列的文件，修改一条只改变该行，插入的条目也排入相应位置；原本未按此顺序排列的文件，第一次修改时整体重排一次，此后与前者相同。

**「设置编码」是两种操作，界面须分别提供：**

| | 字节 | 文字 | 用途 |
|---|---|---|---|
| **转换**：修改树中目录的 `charset`，保存时按新编码写出 | 改变 | 不变 | 改为 UTF-8 等编码 |
| **重新解读**：按新编码从磁盘重新读取该目录，替换其子树。`oto.ini` 声明了 UTF-8 的目录只能按 UTF-8 读取，其他编码被拒绝 | 不变 | 改变 | 当初选错编码导致乱码，或未选择编码导致目录被跳过 |

编码由用户选择并记录在 `hello-config.json` 中，库不判断原版 UTAU 能否读取所选的编码。重新解读替换该目录的子树，与重新读取相同，是一个可撤销的步骤，见「磁盘变化的处理」。用户在打开时选择的编码须在下次保存时记录，否则每次打开都会再次询问。

重新解读也可以一次作用于多个目录（`reread()` 的列表重载），构成一个撤销步骤。某个目录未能重新读取时报告原因，其余目录照常读取。音源窗口据此提供整个音源的重新解读：对话框与打开时的编码对话框相同，列出树中的目录，各以当前编码为初值，只重新解读编码改变的目录。没有文本文件的目录与 `oto.ini` 声明了 UTF-8 的目录不列出。打开时被排除的目录也不列出，这些目录仍由目录树逐个读入。

### 保存时写入哪些文件

**判断有没有改动不比较内容**（作者 2026-10-11 决定）。编辑中的内容只有一份，即树。磁盘状态不保存内容的副本，也不为判断改动计算哈希。写入哪些文件由撤销历史决定，磁盘上的文件有没有被其他程序修改按 git 的做法判断。这一节取代此前「与基线比较」与「保存时重读文件比较摘要」的做法（2026-10-12 实现）。

**每个步骤记下它碰过的文件。** 事务提交时，会话按改动的槽把步骤对应到文件：

| 改动 | 碰过的文件 |
|---|---|
| 目录的 oto 条目 | 该目录的 `oto.ini` |
| 根目录的 `character`、`prefixMap`、`readme` | 根目录相应的文件 |
| 目录的 `charset` | 该目录的全部文本文件与 `hello-config.json` |
| 目录的 `fileNameEncoding` | 该目录的 `hello-config.json` |
| 目录的加入与替换（重新读取） | 该目录的全部文本文件。编码不变，因此不碰 `hello-config.json`，用户指定编码的重新解读另把它的同步点记为无效 |
| 目录的移除（重新读取） | 不写入。撤销后目录回到树中，磁盘状态中没有它，保存时作为新目录写入它的全部文件 |

`hello-config.json` 只在上表的改动碰过它，或其同步点无效时写入，只编辑条目时不重写。打开时由用户选定编码的目录，同步点无效，下次保存即写入编码。

**每个文件有一个同步点**，即树中该文件的内容与磁盘一致时所处的步：

- 打开时为当前步。
- 保存写入该文件之后为当前步。保存未写入的文件，同步点不变。
- 重新读取替换一个目录之后，该目录的文件为重新读取之后的步，因为此时树按磁盘读入。
- 撤销历史被截断时，被截掉的步骤若位于某个文件的同步点与当前步之间，或同步点本身被截掉，该文件的同步点记为无效。最早的步骤被丢弃时，会话仍记得这些步骤碰过的文件，判断不受影响。
- 打开时用户选择了编码的目录（`rememberCharset()`），以及用户指定编码重新解读的目录，其 `hello-config.json` 的同步点记为无效，下次保存即写入编码，取代此前的「记录编码」标记。

**保存时写入的文件**：同步点无效的文件，以及同步点与当前步之间的路径上有步骤碰过的文件。转换编码碰过该目录的全部文本文件，因此在新编码下字节不变的文件也会重写。撤销回保存时的步，路径为空，不写任何文件。先编辑目录 A 后撤销，再编辑目录 B，只写 B 的文件。撤销一次重新读取，路径上有那次重新读取，该目录的文件以撤销后的内容写回，与「磁盘变化的处理」相同。未经编辑的文件不重写，因此使用 LF 换行或未排序的文件不会因保存而改变。

**磁盘上的文件有没有被其他程序修改**，按 git 处理 racy-clean 的做法判断（git 的 `Documentation/technical/racy-git.txt`）：

- 磁盘状态为每个读取或写出的文件记下修改时间、大小与内容的摘要。摘要在读取或写出时顺便算出，文件此时本来就在内存中。
- 保存前，对每个要写入的文件取一次属性。修改时间或大小与记下的不同，即视为被其他程序修改，拒绝整次保存。
- 属性相同而修改时间距记下属性的时刻不足时间精度（与目录指纹的 `isRacy()` 相同），属性不可信，只有这时才读取文件比较摘要。
- 其余情况不读取文件。

**`hello-config.json` 打开时读取一次，此后磁盘上的这个文件一概不管**（作者 2026-10-11 决定）：不检查，不报告，不重新读取，保存前也不检查是否被修改，按上面的规则需要写入时直接覆盖。内存中只留一份：编码与文件名记录在树中，磁盘状态只留打开时读到的本版本不认识的字段，供写入时写回。外部删除了配置时，在下次需要写入之前，磁盘上没有配置，下次打开会重新询问编码。配置本不应由其他程序修改，这一后果可以接受。

**`VoiceBankFileSystemState::save()` 由调用方告知写入哪些文件**，自身不判断改动。会话按上面的规则求出要写入的文件。不经过会话的调用方（命令行工具与测试）没有撤销历史，自行指定要写入的文件。

### 编码的选择与记录

**每个目录一个编码，用于其中全部文本文件**（`oto.ini`，根目录另有 `character.txt`、`prefix.map`、`readme.txt`），记录在该目录的 `hello-config.json` 中。

- `oto.ini` 声明了 UTF-8 时，整个目录即为 UTF-8，不询问，也不看记录。
- 否则取自记录。
- **二者都没有时，弹窗由用户选择。** 选择器（`VoiceBankCharsetSelector`）收到每个目录每个文本文件的原始字节（`VoiceBankDirectorySource::contents`），供界面按候选编码逐个预览。确认即记录，记录在下次保存时写入。
- **打开时一个音源只问一次**（作者 2026-09-29 决定）：打开音源时，所有未确定编码的目录经 `selectCharsets()` 一次交给选择器，界面在一个对话框中列出这些目录。选择器默认逐个调用 `selectCharset()`，命令行工具与测试的选择器因此不变。重新读取时新出现的目录仍逐个询问。
- **对话框预选最可能的编码**（作者 2026-09-29 决定）：按 `TextCodec::ranked()` 给候选排序，先选中读得最通顺的；某个目录用它会出现不合法的字节时，该目录改选对它最通顺的；读不了的候选标灰。这只是默认选中项，仍由用户确认，符合 [`Interchange.md`](Interchange.md)「默认编码可以推测，最终编码不可以」与 `CLAUDE.md` 的规定。UST 的编码对话框同样预选。
- 打开后重新读取一个目录时，用会话记着的编码，新出现的文本文件也按它读取，不再询问。
- 打开工程时，工程与其关联的音源的编码一并确定：UST 的编码与该音源每个未确定编码的目录都在打开时选定并记录，此后原版 UTAU 能否读取不在考虑之内。
- **只打开工程时，选定的编码在确认后立即写入**该目录的 `hello-config.json`（`ProjectDocument::loadVoiceBank()`），因为此时没有音源的保存可以等待。写入只涉及配置文件，音源的其他文件不变；写入失败只给出警告，音源照常使用，下次打开时再次询问。用户跳过的目录不记录。

编码不按文件分别记录。某个文件实际使用的编码与目录不同时，其中不合法的字节读作 U+FFFD，打开后即可看出，由用户处理。

### UTAU 音源路径的两种相对写法

UTAU 对带 `%VOICE%` 前缀的音源路径与不带前缀的相对路径采用不同的解析基准：`%VOICE%bank` 指向 UTAU 安装目录下的 `voice\bank`，而 `bank` 指向 `utau.exe` 所在目录下的 `bank`（实测见 [`claude/utau-voicedir-cachedir.md`](claude/utau-voicedir-cachedir.md)）。`Track::voiceDirectory()` 分别以音源文件夹与 `VoiceLocations::relativeBase` 解析这两种写法。工程属性的音源目录框显示 `VoiceDir` 的原值，因此两种写法不会混同，规范化规则见 [`Widgets.md`](Widgets.md)「工程属性」。

### 文件名编码错解的处理（尚未实现）

**磁盘上的文件名可能已被错解。** 常见的成因是音源以 Shift_JIS 等编码写出文件名后打包（zip 不带 UTF-8 标志），在另一种代码页的系统上解压，解压程序按本机代码页解释这些字节，磁盘上保存的就是错误的 Unicode 文字。例如日文音源在中文 Windows 上解压，`あ.wav` 变为 `偁.wav`。`charset` 只描述文本文件的内容，不描述文件名。

**原版 UTAU 能使用这样的音源。** UTAU 以 ANSI 接口按本机代码页处理文件名：`oto.ini` 中的文件名是 Shift_JIS 字节，磁盘上的错解名按 GBK 编码回去正好是同样的字节，二者在字节层面一致。HelloUtau 以 Unicode 接口读取，`oto.ini` 按正确的编码解码后，条目中的文件名与磁盘上的名字不一致。

**两种做法都提供**（作者 2026-10-11 决定）：

1. **按错解读取，不改磁盘**，与 UTAU 的结果相同。用户不转换也必须能使用这样的音源。
2. **转换**，把磁盘上的名字改成正确的名字，作为可选的操作。转换之后，在错解时的代码页下 UTAU 无法再使用这个音源：正确的名字按该代码页编码得到的字节与 `oto.ini` 中的字节不同。因此转换必须由用户明确选择，对话框中写明这一后果。

#### 按错解读取

在每个目录的 `hello-config.json` 中记录用户对文件名的决定，独立于 `charset`。两个编码的方向明确，以便还原已经产生的错解，而不是只记录一个「正确编码」的名称：

```json
{
  "charset": "Shift_JIS",
  "fileNameEncoding": {
    "original": "Shift_JIS",
    "misdecodedAs": "GBK",
    "files": {
      "misdecoded": ["_偁媧偁揻.wav"],
      "correct": ["_あ長.wav"]
    }
  }
}
```

格式以 [`note.md`](note.md)「HelloUtau 标记文件」为准，由 `VoiceBankConfiguration::FileNameEncoding` 读写。各字段的语义：

- `original` 是文件名创建时的原始字节编码。
- `misdecodedAs` 是这些字节被错误解释并写入文件系统时使用的编码。
- **记录表示用户已经决定**（作者 2026-10-12 决定，取代 2026-10-11 的「不设简写」）。用户在询问中确定了一个目录的全部名字之后，包括选择按原样使用，该目录的文件名即已决定，之后新增的名字不再询问。记录因此有三种形式：
  - 空对象 `{}`：名字全部正确，新增的名字同样按原样使用。
  - 只有两个编码：名字全部错解，新增的名字同样还原。还原失败的名字按原样使用，不报告警告，因为这样的名字不可能是错解的。
  - 两个编码加 `files`：一部分名字错解。`misdecoded` 列出错解的物理名称，读取时按两个编码还原。`correct` 列出本来就正确的名称，不还原。目录中每个非 ASCII 的音频文件名与子文件夹名都必须出现在两个列表之一，两个列表中都没有的名字是新增的名字，状态无法推断，须由用户判断。列表只存物理名称，逻辑名称总是按两个编码求出。
- **写入时归一。** 没有错解的名字时写空对象。能还原的名字全部错解时写只有两个编码的形式，不能还原的名字不影响这一判断。其余情况写 `files`。
- **只记录音频文件与子文件夹**，即音源模型使用的名字（作者 2026-10-11 决定）。重采样器在 wav 旁写出的 `.frq` 等文件沿用 wav 的错解名，若也须记录，每次渲染都会产生新增的名字。磁盘检查出于同一理由只比较这两类名字，见 `VoiceBankDirectoryStamp`。
- ASCII 名字不记录，因为它在这些编码中不会被错解。
- 列出的名字在磁盘上已不存在时，下次保存把它从列表中去掉。`misdecoded` 中的名字不能还原时报告警告，按物理名称处理。
- 缺少 `fileNameEncoding` 时不对文件名做任何转换，打开时按下文「询问的时机与对话框」询问。
- 该记录只描述文件名，不改变同一目录中文本文件的 `charset`。

实现时为每个路径同时保留物理名称与逻辑名称。物理名称用于实际打开、读取、重命名与删除文件。逻辑名称用于显示、与 `oto.ini` 解码后的文件名匹配，以及写出需要引用文件名的文本。还原时先按 `misdecodedAs` 把物理名称编码为字节，再按 `original` 解码为逻辑名称。**每个目录的记录只管该目录中的名字**，即其中音频文件的名字与这一层子文件夹的名字（作者 2026-10-11 决定）。子文件夹中的名字由子文件夹自己的 `hello-config.json` 管理，每一层分别记录，不能只修正最底层的 wav 文件名。音源根文件夹本身的名字不还原。

**还原函数无法区分错解的名字与正确的名字**，见「实测」，因此每个名字的状态由用户确认后记录，不由还原是否成功推断。

边界处理：

1. 用户在编码选择界面明确选择文件名编码与每个名字的状态，库不根据乱码的外观自动猜测。默认选中项可以按 `oto.ini` 的条目推测，见下文「推测」。
2. 还原后产生相同的逻辑名称时，保留物理路径并报告冲突，禁止静默覆盖或随机选择条目。
3. 无法往返、路径不存在或记录无效时，保留物理名称并报告警告，音源在用户处理后仍可使用。
4. 读取时只采用目录自己的记录，不沿用上一层目录的记录，因此单独复制出去的子文件夹带着自己的记录。没有记录的目录中的名字不还原。保存时不改写未涉及的目录的配置。
5. 保存文本时用逻辑名称生成 `oto.ini` 的内容，实际的文件操作始终使用物理路径，以免因显示名称变化而误删或误写文件。
6. 以后提供重命名时，必须同步更新物理名称与逻辑名称的对应，并以一次可撤销的操作完成，不能只修改显示的文字。

**询问的时机与对话框**（作者 2026-10-12 决定，取代 2026-10-11 的「新增的名字」）：

- **打开时与文本编码一起询问。** 打开音源窗口、打开工程或为工程设置音源时，编码对话框分为两部分：文本编码，即每个目录一个编码的原有询问，以及文件名，即每个目录须确认的名字。文件名部分依赖文本编码，因为推测要用解码后的 `oto.ini` 条目，用户改变某个目录的文本编码时，该目录的文件名部分随之重新计算。
- **文件名部分列出两类目录**：记录有 `files`、而有两个列表都没有的非 ASCII 音频文件名或子文件夹名的目录，以及没有记录、而有非 ASCII 的音频文件名或子文件夹名不被 `oto.ini` 的任何条目按原样指向的目录（作者 2026-10-12 决定）。后者包括没有 `oto.ini`、`oto.ini` 为空与条目全部找到文件的目录。前者只列出新增的名字，后者列出全部非 ASCII 的音频文件名与子文件夹名，因为记录须包括全部名字。按当前的编码组合没有一个这样的名字能还原时不询问。
- **每个名字一行**：勾选框、磁盘上的名字、还原后的名字，勾选表示错解。默认勾选能还原的名字，但磁盘上的名字与 `oto.ini` 的条目完全一致时不勾选，与转换对话框的规则相同。不能还原的名字不列出，确定时记入 `correct`。
- **用户可以对没有记录的目录选择按原样使用。** 这同样是决定，写入空对象的记录，之后不再询问（作者 2026-10-12 决定，取代「不建立记录，下次再问」）。想下次再问的用户选择「稍后」。
- **默认按原样使用**：没有记录、推测没有提出编码组合的目录，同时满足以下条件时默认选择按原样使用（作者 2026-10-12 决定）。大多数音源的文件名没有错解，这些条件描述的正是这种情况。
  - 有 `oto.ini`，且条目中按原名找到文件的不少于 75%，按条目的不同文件名计数。
  - 全部待确定的名字都能以该目录的文本编码表示。
- **不满足上述条件、推测也没有提出编码组合时**，编码组合预选为（该目录的文本编码，本机的 ANSI 代码页），二者相同时被错解成的编码改取候选中第一个不同的编码，名字按「每个名字一行」的规则勾选。对话框注明这些名字无法据条目推测编码。
- **回答的去向。** 音源窗口打开时，回答成为打开时的内容，该目录配置的同步点无效，下次保存写入记录。只打开工程时，回答立即写入该目录的 `hello-config.json`，与选定的文本编码相同。
- **之后检查磁盘发现新增的名字时不弹窗**，只在窗口底部的提示条中提示，与新增的音频文件和目录相同。提示条提供按钮，打开同一个对话框的文件名部分，确定为一个撤销步骤「确定文件名」。只打开工程时不响应磁盘变化，因此不再询问。
- HelloUtau 自己新建的文件写成错解后的名字，记录有 `files` 时直接记入 `misdecoded`，不询问。

**推测**（作者 2026-10-12 决定）：推测只决定默认选中项，由用户确认，不代替记录，符合 `CLAUDE.md` 与 [`Interchange.md`](Interchange.md)「默认编码可以推测，最终编码不可以」。依据是 `oto.ini` 的条目能否对上磁盘上的文件，而不是名字看起来是否像乱码。

- 只对没有记录、`oto.ini` 中有条目指向不存在的文件的目录推测。有记录的目录沿用记录的编码。没有条目可以比对的目录不推测，按上文「默认按原样使用」与其后一条预选。
- 候选的编码组合是 `TextCodec::ustCandidates()` 中两两不同的编码组成的（原本的编码，被错解成的编码）。对每个组合，把磁盘上的非 ASCII 音频文件名按该组合还原，统计还原后的名字与找不到文件的条目的文件名一致的个数。条目按该目录的文本编码解码，因此能对上的组合的原本的编码通常就是文本编码，文件名部分随文本编码重新计算。
- 取个数最多的组合。个数相同时，原本的编码是该目录的文本编码者优先，其次是被错解成的编码是本机的 ANSI 代码页者，再次按候选的顺序（作者 2026-10-12 决定以文本编码优先）。所有组合的个数都为 0 时不提出。
- 对话框注明推测的依据与所用的文本编码，例如「按 Shift_JIS 读取的 `oto.ini` 中有 12 个条目找不到文件，按 Shift_JIS 被错解为 GBK 还原后对上 12 个」。列出的名字中有既不对上找不到文件的条目、也不被条目按原样指向的，另注明其个数，这些名字的状态无法据条目确定。用户可以改选编码组合，名字的勾选随之重新计算。

**随 wav 命名的文件**（作者 2026-10-11 决定）：频率表等文件的名字与 wav 相随，但规则各不相同。`.frq` 只是改名，moresampler 的 `desc.mrq` 是一个目录一份，其中按 wav 的名字记录条目，须改写内容。因此改名的规则由频率表格式的驱动 `FrequencyFormat` 提供，与读取、删除一样是驱动的一项职责：接口是批量的，一次给出一个目录中全部「wav A 改名为 B」的对应，驱动返回须执行的改名或改写，`desc.mrq` 这样每个目录一份的文件因此只改写一次，附属的缓存（如 mrq 的 `.llsm`）一起处理，这些操作与 wav 的改名一起纳入保存时的检查、执行与回滚。FrequencyEditor 插件登记的 frq、dio、mrq 各自实现，插件登记的其他格式同样经此扩展。`FrequencyFormat` 现在是只读的接口，实现转换时加入这一项，规则见 [`FrequencyTables.md`](FrequencyTables.md)「格式驱动」的「改名」。

实现前还须确定以下几点（2026-10-09 补充，作者同意先记为待定）：

- **还原不一定可逆。** 原始字节按错误编码解读时，若遇到该编码中不合法的字节序列，解压程序可能已把它替换为 `?` 或 `_` 写到磁盘上，这部分信息已经丢失。此时报告警告，由用户在磁盘上手动改名。记录只存物理名称，不提供手动指定逻辑名称的对应（作者 2026-10-11 决定）。
- **不记录的文件。** `character.txt` 引用的图像、`readme.txt` 中提到的文件名不在记录中，读取时怎样找到错解名的图像尚待确定。
- **新建与重命名的文件名。** 加入音频文件或重命名文件时，写到磁盘上的名字须与该目录现有的名字一致，即按 `misdecodedAs` 错解后的名字，这样 UTAU 仍能使用（作者 2026-10-11 决定）。错解后的名字不存在时报错并拒绝，不写入其他名字：逻辑名称无法按 `original` 编码，或编码得到的字节按 `misdecodedAs` 解码含无效字节序列。HelloUtau 目前不新建也不重命名音频文件，这一规则在导入、录音等功能出现时实现。
- **Unicode 规范化形式。** macOS 上的文件名可能是分解形式（NFD，例如 HFS+ 一律如此），与 `oto.ini` 中的组合形式（NFC）逐字节不同。比较前须统一规范化形式，否则含浊音符号的假名无法匹配。

验证包括：Shift_JIS 文件名在 GBK 系统上的音源，含错解目录名的嵌套音源，同名 wav 与别名的匹配，新旧名字混杂的目录，新增的名字，逻辑名称的冲突，重新打开与保存后的路径保持，以及没有该记录时旧音源的兼容。

#### 转换

**文本编码与文件名编码的转换在同一个对话框中进行，作为一次可撤销的操作**（作者 2026-10-11 决定）。二者相互独立：文本编码改的是文件内容的字节，文件名编码改的是磁盘上的名字。

- **入口**：音源窗口的「Convert Encodings...」。对话框分为两部分，用户可以只做其中一部分：
  - **文本**：按目录勾选，每个勾选的目录选择新的编码，该目录的全部文本文件一起转换（沿用「每个目录一个编码」，作者 2026-10-11 决定）。这与单个目录的 Convert Encoding 相同，文字不变，字节改变。
  - **文件名**：选择两个编码，即文件名原本的编码与它被错解成的编码。目录已有 `fileNameEncoding` 记录时以记录为初值，否则按「推测」预选。推测不出时，被错解成的编码预选本机的 ANSI 代码页，原本的编码按 `TextCodec::ranked()` 预选新名字中无效字节最少的候选。二者都由用户确认。用户在预览中勾选错解的名字，再选择做法，做法作用于全部勾选的名字（作者 2026-10-11 决定，按错解读取的设置不另设命令）：
    - **只按错解读取**：勾选的名字记为错解，该目录其余的非 ASCII 音频文件名与子文件夹名记为正确，按「写入时归一」写入记录，不改磁盘上的名字。没有勾选任何名字的目录写入空对象。
    - **改名**：在保存时把勾选的名字改正，对话框为此写明转换后 UTAU 在错解时的代码页下无法使用这个音源。
    - 没有勾选的名字视为本来就正确，不还原，也不改名。「改一部分名，其余继续按错解读取」须分两次操作，先只按错解读取，再改名并只勾选其中一部分。
- **新名字**：与按错解读取的还原规则相同，即按被错解成的编码编码为字节，再按原本的编码解码，macOS 上的名字先统一为 NFC。**全 ASCII 的名字不参与转换**，`oto.ini`、`hello-config.json` 等保留文件因此自然排除。只列出满足全部条件的名字：编码为字节无损，按原本的编码解码没有无效字节，结果与原名不同。已经改正的名字往往也满足这些条件，还原的结果是乱码，见「实测」，因此由默认的勾选与用户排除。
- **预览**：列出音频文件与子文件夹中每一个能还原的名字，形式为「当前名字 → 新名字」，每项可以取消勾选。目录已有记录时按记录勾选，记录中没有的名字按没有记录时的规则勾选。没有记录时全部勾选，但物理名称与 `oto.ini` 的条目完全一致的名字不勾选，依据是条目而非名字的外观，因此不属于猜测。随 wav 命名的文件不单独列出，由登记的处理者随 wav 处理。无法转换的名字（信息已经丢失）单独列出警告，不改名，由用户手动处理。
- **范围**：文件名的转换涉及整个音源的所有层级（作者 2026-10-11 决定，不提供只转换某个子文件夹的功能，需要排除的名字在预览中取消勾选）。音源根文件夹本身不改名，因为工程与设置中记录着它的路径。
- **撤销与保存**：确认后只修改文档，即目录的编码、文件名编码的记录与文件和文件夹的名字，整个操作是一个撤销步骤。**磁盘上的改名与文本一样在保存时执行**（作者 2026-10-11 决定）。保存时先完成全部检查，包括冲突（两个名字变为同一个名字、目标名字已存在）、无效的名字与被占用的文件，任何一项不通过即拒绝整次保存并列出原因。目录由深到浅改名，中途失败时把已经改过的名字全部改回。保存之后撤销，会在下次保存时把名字改回。
- **记录**：保存后，改过名的名字记为正确，因为磁盘上的名字已经正确，记录按「写入时归一」重写。一个目录没有错解的名字时写入空对象（作者 2026-10-12 决定，取代 2026-10-11 的「删除记录」）。`oto.ini` 不改写：按正确的文本编码读出的条目本来就是正确的名字，改名之后自然对应。
- **对现有模型的要求**：文件与文件夹的名字须进入编辑层的文档，`VoiceBankFileSystemState::save()` 须支持改名并在失败时回滚。没有条目的 wav 现在由磁盘状态记录的音频文件推导，改名后须以文档中的名字为准。

#### 实测

2026-10-11，作者的朋友提供的 `SiHaoYu_VCV_JP`，文件名为中文系统上错解的日文：973 个名字中 37 个为 ASCII，文件夹名均为 ASCII。936 个非 ASCII 名字按 GBK 编码再按 Shift_JIS 解码全部无损，例如 `_偁媧偁揻.wav` 还原为 `_あ吸あ吐.wav`，`_偁丒偁_wav.frq` 还原为 `_あ・あ_wav.frq`。同名的 `.llsm` 与 `.frq` 也是同样的错解名。调查使用 Python 的 gbk 与 cp932，二者与 Windows 的转换表只在极少数字符上不同，实现使用 `winacp`。

**已经正确的名字也能「还原」。** 把这 936 个还原后的名字再还原一次，691 个仍满足全部条件，结果是乱码，例如 `_あ長.wav` 变为 `_､｢餃.wav`。平假名在 GBK 中有编码，其字节按 Shift_JIS 解读为合法的半角片假名。因此还原函数无法区分错解的名字与正确的名字，错解的名字须由记录列出。

**推测的结果**（2026-10-12，`MisdecodedNameQuestion`）：这个音源根目录的 `oto.ini` 为空，没有条目可以比对，不推测。`audioSample_C3` 中 148 个条目找不到文件，在全部候选组合中只有「按 Shift_JIS 写出、被错解为 GBK」能使条目对上文件，148 个全部对上，148 个名字全部默认勾选。`audioExtra_C3` 为 29 个，同样全部对上。名字全为 ASCII 的 `audioExtra_Breath` 不提问。

**不合法的字节读作 U+FFFD。** 按选定的编码解码，不合法的字节序列逐个替换为 U+FFFD，只要文件仍能解析就不算失败：`readme.txt` 里写错几个字，不影响音源可用。

- 读取时每个文件分别报告不合法字节序列的个数，作为警告；
- 选定的编码照常记录，不因解码出错而不记录，因为编码是用户选的；
- **要写出的文本中含有 U+FFFD 时，拒绝写这个文件**，并一次列出全部位置。这是为了防止选错编码时保存破坏原文；没有修改的文件不会被重写，不受影响。

**`hello-config.json` 由 HelloUtau 管理，用户不得修改，外部修改不重新读取。**

| 时机 | 处理 |
|---|---|
| 打开时读得出 | 按记录的编码解码，没有记录的文件按上述规则询问 |
| 打开时读不出（不是合法的 JSON、同名的是目录、无权读取） | 视为没有记录，按「编码不能确定」询问，并给出警告。保存时覆盖它 |
| 打开后被外部修改、删除或新建 | 不检查，不报告，不弹窗，也不重新读取（作者 2026-10-11 决定，取代此前的 `VoiceBankChanges::config`） |
| 其他文件变化，重新读取该目录 | 使用会话记着的编码，不读取磁盘上的配置。打开后在外部改动的编码因此不生效 |
| `reread()` | 不受影响，编码由用户指定 |
| 保存 | 按「保存时写入哪些文件」需要写入时，不读取磁盘上的配置，**直接覆盖**，不按「拒绝替换已被其他程序修改的文件」处理。写入的内容是树中的编码与文件名记录，加上打开时读到的未知字段。外部加入的字段随覆盖丢失 |
| 保存时同名的是目录，或无法写入的文件 | 在检查阶段报告错误，整次保存不写任何文件。无法写入的判断方法：检查阶段以追加方式打开已存在的该文件，不改变其内容 |

新目录不论其中有什么，都照常报告为新目录；何时重新读取、怎样提示，由界面决定。另存为不变：复制其他文件时本来就跳过这个文件名，新文件夹中的配置由写出过程生成。

保存写入的文件随即计入目录指纹，此后的检查不把它们当作外部修改。同一目录中未写入的文件仍按原来的指纹比较。检查磁盘不比较 `hello-config.json`。

### 磁盘变化的处理

**与 UTAU 相同，取决于当前打开的内容。**

| 打开的内容 | 是否响应文件系统变化 |
|---|---|
| 仅工程 | **不响应。** 工程打开时获得的是音源的一份快照，此后音源在磁盘上的任何变化都不影响已打开的工程，直到有人编辑并保存该音源 |
| 该音源的编辑界面 | **不得遗漏任何变化。** 界面显示的内容可能已不存在于磁盘上，必须得知这一情况 |

因此 `VoiceBankCheckScheduler` **随音源编辑界面存在**：界面打开时创建，关闭时销毁，库中不需要「仅打开工程」的开关。

编辑界面打开时的流程：

1. 调度器发出 `checkNeeded(places)`，界面调用 `checkDisk(places)`。**只检测，不修改音源。**
2. 检测结果分为两类，提示方式不同：

| 变化 | 提示方式 | 用户同意后 |
|---|---|---|
| 目录中的 `oto.ini` 被修改，根目录的 `character.txt`、`prefix.map`、`readme.txt` 被修改；目录被删除 | **醒目的弹窗**，询问是否重新读取。用户可以不读 | 重新读取，替换相应子树，**作为一个可撤销的步骤** |
| 出现未收录的 wav（打开时发现，或此后新增）；有条目的 wav 被删除；出现新的目录 | 窗口中相应条目或空白处的提示，不打断操作。wav 已不存在的条目，在条目表格的对应行上显示警告 | 未收录的 wav：插入条目。被删除的 wav：不自动删除其条目，由用户处理。新的目录：读取该目录，作为一个可撤销的步骤 |
| `hello-config.json` 被修改、删除或新建 | 不检查，不提示 | 不读取，保存状态不变。见「保存时写入哪些文件」 |

3. 用户选择重新读取后，调用重新读取的函数。该函数会再次检查磁盘：检查后又被删除的目录不读取，又恢复的目录不删除。它同时更新账本，并返回各目录的新内容，由会话在一个事务中替换子树。若该目录有未保存的修改，两个版本同时存在，保留哪个由用户选择，库不替用户决定。会话的接口是 `VoiceBankSession::checkDisk()`、`reloadFromDisk()`、`reloadAllFromDisk()` 与 `reread()`：替换目录的事务标记为读自文件，不校验约束；重新读取后未能读取的子目录离开树，进入 `excludedDirectories()`，反之则进入树；只有音频增减时不产生撤销步骤。

**撤销一次重新读取。** 树回到重新读取前的内容，账本不回退：账本记录的仍是新读取的磁盘状态。撤销后，那次重新读取位于该目录各文件的同步点与当前步之间（见「保存时写入哪些文件」），因此保存时以撤销后的内容覆盖磁盘，即用户选择了自己的版本。若撤销的重新读取增删了目录，树中的目录与磁盘不再一一对应，保存时按以下规则处理，不报告错误：

- **树中有而磁盘上没有的目录**（撤销了「目录被删除」）：保存时创建该目录并写入其 `oto.ini` 与 `hello-config.json`。只有无法创建时才报告错误：该路径已是一个文件而非目录，或已是一个无权访问的目录。目录可以访问而其中已出现同名文件时，按「拒绝替换已被其他程序修改的文件」处理。
- **磁盘上有而树中没有的目录**（撤销了「目录被新增」）：保存时不删除，也不写入该目录。此后的检查将其报告为新的目录，与其他未处理的变化一样重复报告，但只以不打断操作的方式提示，因此撤销之后不会再次弹窗。

`VoiceBankFileSystemState::checkDisk()` 按上表的两类分开报告：`changed`（文本文件被修改）与 `removed` 属弹窗类，`audio`（只有音频文件增减）与 `added` 属提示类。`audio` 的应用不经用户决定：只更新没有条目的样本，即合成时按文件名查找的样本，不改动条目与未保存的修改，也不进入撤销栈，因为它只反映磁盘上的事实。

**不遗漏变化依赖以下三项机制，缺一不可：**

- **检测到的变化在重新加载之前每次都会重复报告。** 某次检查的结果被错过，下一次仍会报告。
- **通知仅作为提示。** 无论监视器是否正常工作，调度器都定时进行全量核对（默认 60 秒）；监视器不可用时（网络驱动器、缺少 `hello-fswatcher`、根目录已删除），改为轮询（默认 5 秒）。核对只列出目录而不读取文件，因此定时执行的开销可以接受。
- **修改时间不可信时比较内容。** 对于修改时间距取指纹 2 秒以内的文本文件（FAT 的时间精度为 2 秒），即使指纹相同也要再比较摘要，与 git 的 racy-clean 机制相同。

**必须提供手动刷新。** `reloadAllFromDisk()` 完全忽略指纹，重新读取全部内容，对应 UTAU 的刷新按钮。在时间戳不可靠的网络驱动器上，或用户认为内容有误时，这是始终可用的退路。

**不属于本机制的范围：** wav 的内容。音源模型只关注文件名；wav 被重新录制时，渲染缓存的键包含样本的大小和修改时间，会自行检测到变化。重采样器在 wav 旁边写出的 `.frq`、`.llsm` 也不视为变化，否则每次渲染都会使音源显示为已修改。

### 编辑与约束

音源的记录与约束：

| 记录 | 约束 |
|---|---|
| oto 条目 | 文件名非空；同一 wav 的各条目别名不重复（别名为空时以文件名的主干计） |
| `prefix.map` | 键即音高，在 24 到 107 之间（C1 到 B7），写作不带符号与前导零的十进制数。树中的键是文本，同一音高的另一种写法会成为第二个键 |

**不同 wav 登记同一别名，不受约束，查找时用哪一条未定义。** 调用方不得依赖其结果；现有实现返回先读到的一条。条目在文件中的先后同样不表示任何含义，见「读写的保证」中 `oto.ini` 的排序。

oto 的五个时间参数不设范围：`cutoff` 为负表示从偏移量起算的长度，是正常写法。每个条目保存五个数字的原有写法，未修改的条目逐字节写回。原有写法只在仍能解析为当前数值时写出，因此数值被修改后自然按最短写法重写，无需清空；改回原值时恢复原有写法。空的数字字段按 0 读取，数值仍为 0 时照样写空；新插入的条目没有原有写法，写出 `0`。

第一批领域函数：修改 oto 条目、插入与删除条目（包括收录未收录的 wav）、写入与删除 `prefix.map` 的一项、转换编码。修改别名只是一个字段赋值，由句柄与 `set` 命令完成，不另设领域函数。每个函数有对应的命令。

验收标准第 7 项（每个节点操作和领域函数都有对应的命令）由**领域函数登记表**保证。C++ 无法枚举一个类的静态函数，因此领域函数所在的类声明为 `Q_GADGET`，每个领域函数标记为 `Q_INVOKABLE`，由 moc 生成的元对象列出全部函数名。命令表的每一项注明它所调用的领域函数，由 `ProjectCommands::domainFunctions()` 等返回「函数名到命令名」的登记表。测试将元对象列出的函数名与登记表对照：新增领域函数而未添加命令，或命令指向已不存在的函数，测试都会失败。剩下的遗漏只有一种，即新函数忘了标 `Q_INVOKABLE`，这在审阅时一眼可见。

实测使用夏语遥音源（`Xia_Voice_Bank_SZH`）的副本：根目录与四个子目录各有一份 `oto.ini`、`prefix.map`、单个 wav 带大量别名、空的 `oto.ini`、五个数字全空的条目，且 `readme.txt` 为 Shift_JIS 而其余文件为 ASCII。实测只修改副本。

### 音源在磁盘上不完整

**根目录出了问题，磁盘上的音源即已非法，编辑器中的树是唯一完好的副本。** 与打开时的规则一致：根目录读不了，音源就打不开。打开之后才出问题的情况有两种：

| 情况 | 如何得知 |
|---|---|
| 根目录被删除或改名 | 检查磁盘报告 `rootNotFound` |
| 根目录原本没有文本文件，此后出现了文本文件，而没有为它选择编码（没有选择器，或用户拒绝） | 重新读取根目录时读成 `leftOut` |

两种情况的处理相同：

- **以醒目的弹窗告知用户**，说明磁盘上的音源已不完整，编辑器中的内容保持不变，保存会把它写回。
- **树不变。** 重新读取时，根目录不移出树，其内容保持读取前的样子；其他目录照常处理。磁盘状态照常更新为新读到的状态，因此根目录显示为已修改，此后的检查不再重复报告。
- **保存时整个写回。** 根目录不存在时，所有目录都按新目录处理：重建文件夹，写入树中的全部文本文件（`oto.ini`、`character.txt`、`prefix.map`、`readme.txt`、`hello-config.json`），各按其编码。根目录读不了时，根目录的文件以树中的内容覆盖外部的修改。
- **wav 无法恢复。** 树中只有条目与文件名，没有音频。根目录被删除后保存，得到的音源只有文本文件，条目所指的 wav 全部缺失，弹窗须说明这一点。
- **写不回去时报错。** 路径已是一个文件，或上级目录无权访问，保存失败，内容仍在树中。此时用户以另存为写到别处。
- 后一种情况也可以按一种编码重新解读根目录（`reread()`），读取成功即恢复为完整。

### 另存为

**另存为把整个音源写到一个新的文件夹。** 用于原位置写不回去的情况，也用于保留一份副本。

- **写入哪些文件由参数决定。** 文本文件总是写入：树中每个目录的 `oto.ini`、根目录的 `character.txt`、`prefix.map`、`readme.txt`，以及各目录的 `hello-config.json`，各按其编码，目录结构与原音源相同。**默认还把原文件夹中的其他文件（wav、图片、说明书等）原样复制过去**；另一个选项是只写文本文件，因为无法确定其他文件中是否含有指向原位置的绝对路径。默认值由设置面板配置，库只接受参数。原文件夹已不存在时只能写文本文件，并告知用户。
- **不在树中的目录。** 未能读取的子目录不在树中，复制其他文件时随原文件夹原样复制过去，在新位置仍不在树中；只写文本文件时不写。
- **目标文件夹须不存在或为空**，否则拒绝，不与已有内容合并。复制不跟随符号链接，与读取音源时相同。
- **另存为之后，会话改为编辑新文件夹。** 原文件夹不再修改，也不再监视。树与撤销历史保持不变，磁盘状态改为新文件夹的状态，此时音源是未修改的。

会话以 `isIncomplete()` 报告音源在磁盘上是否不完整：根目录不存在，或重新读取时根目录已读不了。保存或另存为成功后恢复为完整。界面据此弹窗。

### 保存状态

**音源是否未保存由 `VoiceBankDocument` 判断**（2026-09-29 起，此前由界面自行判断）：它持有会话，记下保存时的步数 `currentStep()`，当前步数与之不等即未保存；记为 -1 表示无论处于哪一步都未保存。标题栏的标记与关闭时的询问仍是界面的事。工程一侧的 `ProjectDocument` 同理。音源的规则：

| 时机 | 保存时的步数 |
|---|---|
| 打开后 | 当前步数；`hasUnrecordedCharsets()` 为真时为 -1 |
| 保存或另存为成功后 | 当前步数 |
| 保存时的步数被丢弃：其后有新的事务截断重做历史（`EditSession::stepsDiscarded`），或最早的步骤被丢弃 | -1 |
| 检查磁盘报告 `changed`、`removed` 或 `rootNotFound`，或 `isIncomplete()` 变为真 | -1 |
| 从磁盘重新读取 | 不变 |

`hasUnrecordedCharsets()` 报告有目录的编码须由下次保存记录，内容却未修改：打开时用户选择的编码经 `rememberCharset()` 标记，或用户指定编码重新解读了目录，二者都使该目录配置的同步点无效。此时保存要写入 `hello-config.json`，因此音源是未保存的。

**外部修改一经检测到，音源即为未保存。** 磁盘上的内容已与树不同，此后无论用户是否重新读取，都须保存一次才回到「已保存」；重新读取后树与磁盘一致时，这次保存不写入任何文件。只有音频增减（`audio`）和新的目录（`added`）不改变保存状态：二者不改动树中的内容，保存时也不因它们写入文件。

重新读取产生一个步骤，当前步数随之离开保存时的步数，因此无需另行处理。用户以另一种编码重新读取后又撤销，回到保存时的步数，显示为已保存，此时磁盘也未改变。修改后又手工改回原值，仍为未保存，与常见的编辑器相同。

### 音源保存后的处理

保存成功后，**所有使用该音源的已打开工程重建映射**，改用新的快照。

**重建映射不修改工程文件，也不改变工程的保存状态。** 这是编辑器内部状态的变化，而非对工程的编辑，因此**不经过本文档所述的事务**：不进入撤销栈，不写入日志，不会使工程变为「未保存」状态。修改内容属于音源，音源有其自身的保存状态。

实现（2026-09-30）：`VoiceBankDocument` 在保存与另存为成功后发出 `saved()`；`Editor` 对每个已打开的工程窗口，若其音源（`ProjectDocument::voiceBank()`）的根目录与保存的音源是同一个文件夹，即以 `ProjectDocument::setVoiceBank()` 换上该会话的快照，不重新读取磁盘。另存为之后音源位于另一个文件夹，原文件夹未变，使用原文件夹的工程因此不受影响。未保存的编辑不传给工程。快照不含未能读取的子目录（`VoiceBankSession::excludedDirectories()`），这些目录的样本在工程中随之不再按文件名找到，直到工程重新读取音源。

## 节点树的实现

节点树、事务与撤销历史由 substate 实现。节点的所有权、动作、事务与存储合成工具的设计见 substate 仓库的 `docs/Design.md`。

**substate 是 `HelloKitEditBase` 与 `HelloKitEdit` 的私有依赖，`ss::` 类型不出现在任何公开头文件中**，只出现在 `HelloKitEditBase` 的扩展接口（`private/` 下的头文件）中。 编辑层以 `NodeId` 引用节点，以本文档所述的类型化槽位和领域函数修改树，并将 substate 的变更通知转换为自己的信号，不使用 qsubstate 的 Qt 信号适配器。substate 的接口变动因此只影响编辑层的实现，「音符是什么、函数的含义是什么」这些困难且有价值的内容不随之变动。这与 `SynthRunner::makeSynthToolProcess()` 采用的是同一种隔离手法。

### 通用层与文档层

编辑层分为两个目标：

- **通用层 `HelloKitEditBase`**，命名空间 `hello::kit::edit`：`EditSession`、`NodeRef`、`Change`、`Slot.h` 与 `CommandSyntax`，以及扩展接口 `include/hellokit/EditBase/private/`：`EditSession_p.h`（派生类经由它安装根节点，句柄经由它按 ID 取得节点，新节点种类经由它注册变更的翻译、日志的写法和校验）、`NodeAccess_p.h`、字段表 `FieldTable_p.h`、按路径的命令 `NodeCommands_p.h`、变更日志 `ChangeLog_p.h` 与 `Validation_p.h`。它不链接 `HelloKitDocument`，因此不可能引用任何文档的结构；这一点由构建保证，而非约定。取得节点时的类型比对只在断言中进行，因为句柄总是对应其自身类型的节点。测试以一棵与 UTAU 无关的树检验通用层。
- **工程层 `HelloKitEdit`**，命名空间 `hello::kit`：`ProjectSession`（派生自 `edit::EditSession`）、槽位表 `ProjectSchema.h`、句柄 `ProjectRefs.h`、领域函数 `ProjectEdits.h`、命令 `ProjectCommands.h`，以及私有的 `ProjectTree`（`Project` 与树的双向转换、节点类型编号与编解码器注册）、字段表 `ProjectFields` 与校验 `ProjectValidation`。句柄的实现直接操作 substate 的节点。

通用层稳定后将移入 substate（依赖 Qt 的部分进入 qsubstate）。第三层命名空间 `edit` 是为此设的过渡：`Slot`、`Range`、`Change`、`NodeRef` 这类通用的名字在移走之前不占用 `hello::kit`，移走时只需更换命名空间，类名不变。扩展接口放在 `private/` 下，文档层以外的代码不应使用。

音源作为第二种文档，以同样的方式在通用层之上实现，同属 `HelloKitEdit`：`VoiceBankSession`（持有树与磁盘状态，`snapshot()` 由树与磁盘状态记录的音频文件组装出 `VoiceBank`）、槽位表 `VoiceBankSchema.h`、句柄 `VoiceBankRefs.h`，以及私有的 `VoiceBankTree`（`VoiceBank` 与树的双向转换）与字段表 `VoiceBankFields`。音源根目录的路径不可编辑，不在树中，由 `rootPath()` 取得。

### 文档层的生成

文档层的代码都由字段表机械地推出，今后由声明文件生成，目前手写，但严格遵守生成的约定，使生成器只需复现它：

- **槽位表**（`ProjectSchema.h`）：每个记录一个命名空间，每个字段一个 `Slot<T>` 或 `ChildSlot`，名称即 `.usth` 的字段名。枚举类型的字段以 `int` 存储，由 `SlotValue` 的特化转换。
- **转换**（`ProjectTree.cpp`）：每个记录类型一对 `treeOf(const T &)` 与 `fromTree<T>(node)`，逐字段对应。无法逐字段对应的字段由手写的转换函数提供，声明中指明，目前只有 `unknownFields`（文档中为 `QJsonObject`，树中为值为 `QJsonValue` 的映射）。
- **字段表**（`ProjectFields.cpp`）：每个记录类型一个 `RecordInfo`，按槽位顺序列出字段的名称、下标、种类（值、记录、列表、映射、数组）、值的 JSON 格式、是否可空与范围，供命令按名称寻址、日志按下标取得名称。值类型的 JSON 格式即 `.usth` 的写法，由 `formatOf<T>()` 的特化提供。列表中的记录与可空的子记录另有一个由 JSON 创建子树的函数。字段可标为**只读**或**不公开**：只读字段拒绝一切命令，只由文档层修改，如读盘得到的事实，或由领域函数与另一字段一同维护的值；限制只作用于该槽位本身，列表只读时其中记录的字段仍可修改。不公开的字段只属于文档层，命令既不能寻址它，也不接受记录的 JSON 中含有它，记录的 JSON 中也不写出它；它仍留在字段表中，因为字段表按槽位顺序列出全部槽位。
- **句柄**（`ProjectRefs.h` / `.cpp`）：每个记录、列表、映射各一个句柄类，每个成员函数是对通用层 `NodeAccess` 的一次调用。按字段的种类有固定的形式：值字段 `f()` / `setF()`；记录字段 `r()`，可选时另有 `setR(std::optional)`；列表字段返回列表句柄（`size`、`at`、`insert`、`remove`、`move`）；映射字段返回映射句柄（`keys`、`contains`、`value`、`setValue`、`remove`）；数组字段 `a()`、`aSize()`、`replaceA()`、`insertA()`、`removeA()`。只读字段只生成读取函数，只读的列表句柄只有 `size` 与 `at`；不公开的字段不生成函数。每个记录句柄提供 `to<类型名>()` 返回副本。句柄与节点的对应（`NodeOf` 的特化）同样生成。
- **节点类型**：每个记录与数组一个用户类型编号，及编解码器的注册。

**生成器必须支持记录的继承**，即使 UTAU 的工程目前没有这种结构。声明中一个记录可以派生自另一个，例如多种轨道都派生自基本的轨道。生成结果须保留这一关系：

- 派生记录沿用基类的槽位下标，自身的槽位接在其后，因此基类句柄的函数原样适用于派生记录的节点。
- 每个派生记录有自己的节点类型编号。基类句柄按 `StructNodeBase` 访问节点，其类型断言接受基类及全部派生类型的编号。
- 句柄保持相同的继承关系（`XTrackRef : TrackRef`）。元素类型为基类的列表，`at()` 返回基类句柄，另提供按节点类型编号判断的向下转换，方式与 `Change::as()` 相同，不使用 `dynamic_cast`。
- 文档的值类型具有对应的继承关系，插入与 `fromTree` 按实际类型分派。

撤销历史由 substate 的存储合成工具保存。第一阶段使用 `MemoryStorageSynthTool`，即内存中的撤销栈。substate 在第二阶段实现预写式日志合成工具后，更换存储合成工具即可获得崩溃恢复，编辑层的接口不变。

### 恢复

恢复由 substate 的日志合成工具发起：读取检查点与日志，重建树与撤销历史，再交给模型，见 substate `docs/Design.md` 的「持久化接口」。日志合成工具尚未实现，恢复的界面流程在其完成后另行规定。

## 参考：dini

[dini](https://github.com/diffscope/dini)（副本位于 `.cache/dini`，读取时为 `ec400da`）是 DiffScope 的实验性内存文档合成工具，与 substate 解决同一类问题：事务、语义变更集、撤销与重做、快照与变更集重放。它采用关系模型（表、按关联值分组的有序列表、父子组合与级联删除、多态变体、标量列、计算列与索引），而非节点树。**只作为设计参考，不作为代码来源**：仓库中没有许可证文件，库本身要求 C++20。

### 待定事项

以下三项来自 dini 的做法，与本仓库当时尚未规定的问题直接相关，须在所列时机之前与作者确定：

| 事项 | dini 的做法 | 须确定的内容 | 时机 |
|---|---|---|---|
| 按事务的合并通知 | 事件分两个阶段：每次写入后发出 AfterApply，提交时发出 AfterCommit，后者携带 `ChangeSet::merge` 的结果。同一项同一列的多次修改折叠为一条，保留第一次的旧值与最后一次的新值，其他操作按原顺序保留 | **已确定：不增加。** 拖动等持续的操作在进行中不修改树，结束时以一个事务写入最终结果，见「变更通知」 | 第三阶段的界面开始之前（已确定） |
| 不进入撤销栈的修改 | `TransactionOptions{undoable = false}` 的事务照常提交与通知，但不产生撤销步骤。撤销历史保持不变，因此撤销其前一个步骤时写回的是该步骤之前的值，**不可撤销的修改被静默覆盖**（测试 `UndoRedoWithNonUndoableBetween`） | **已确定：不采用不可撤销的修改。** 音源编辑中从磁盘重新读取一个目录，作为一个可撤销的步骤，见「磁盘变化的处理」 | 第 5 步（已确定） |
| 恢复数据的结构兼容 | `SynthToolSchema::serializeStructure()` 与 `matchesSerializedStructure()` 比较快照所用的结构与当前结构 | 检查点与日志须记录字段表的指纹，程序升级后遇到结构不同的日志时拒绝重放，而非错误地应用 | substate 日志合成工具与恢复流程的设计 |

### 与现有设计一致之处

- **撤销应用记录的结果。** 钩子与计算列产生的派生操作写入同一变更集，并以 `DerivedChangeLink` 记录其来源操作；撤销与重做直接应用记录的操作，不再运行钩子，因此结果确定。本仓库没有钩子，由领域函数显式组合节点操作，已满足这一点。将来若有自动修正（例如插入音符后调整休止符），可参照因果链接，使日志与界面区分用户操作及其派生操作。
- **挂入列表必须指明位置。** 将一项挂入列表时必须给出目标下标，不隐式追加。本仓库的「转移」记录源与目标两处的父节点与位置，与此一致。
- **回滚按实际方向报告。** 回滚事件携带实际应用的逆变更集，与本仓库「回滚发出的通知与撤销相同」一致。
- **身份在撤销与重做后不变。** 撤销删除、重做插入后，项的 ID 与原来相同，与验收标准第 5 项相同。

### 不采用的做法

- **写入时校验。** dini 的列约束在写入时检查，不满足即拒绝。本仓库将约束推迟到提交时检查，且只拒绝事务新引入的违例，理由见「校验的两个位置」：读取外部 UST 时本就会遇到越界值，中间状态也可以合理地不满足跨字段约束。
- **关系模型与标量值。** 包络、颤音等整体值须拆为多列或序列化为二进制，portamento 等嵌套列表须另建列表容器。节点树与 UST 及 `.usth` 的结构一一对应，没有更换的理由。
- **计算列。** 只能依赖同一项的字段，无法表达「音符的起始 tick 是其前全部音符长度之和」这类跨项的派生状态。
- **区间索引与有序索引。** 分别查询与给定区间重叠的项，以及按排序键查询前后项。UST 的音符首尾相接、互不重叠，目前不需要；将来支持自由摆放的多轨时可以参考。
- **多态变体。** 每个容器有一组封闭的变体，写入其他变体的列被拒绝。本仓库为生成器规定的是记录继承（派生记录沿用基类的槽位下标），见「文档层的生成」。

## 无界面工具

`hellokit/tests/manual/ustedit`，与 `ustconv`、`ustrender` 并列：

```sh
ustedit song.usth --script edits.txt -o out.usth
ustedit song.ust --charset Shift_JIS -o out.ust < edits.txt   # 从 stdin 读取命令
ustedit song.usth --script edits.txt --dump-changes            # 输出变更日志，不写文件
```

输入为 `.usth` 或 `.ust`，脚本按 UTF-8 读取，每行一条命令。除命令外，脚本还可以写 `undo [<次数>|all]` 与 `redo [<次数>|all]`，它们操作撤销历史而非文档，因此不是命令。`--dump-changes` 将每个变更按 JSON Lines 写到标准输出；只有给出 `-o` 时才写文件。任一行失败即停止，不写文件。验收标准第 3、4 项另有自动测试（`test_ProjectCommands`），`ustedit` 用于真实工程。

## 验收标准

1. **往返**：`Project` → 树 → `Project`，两侧逐字段相等。这一项检验物化层，而物化层是采用节点树方案的主要代价。
2. 无界面模式能打开真实工程，执行一串命令，撤销到底后再重做到底，保存后 **UTAU 能正常打开**且内容符合预期。
3. 撤销到底后保存的文件，与未执行任何命令时保存的文件**语义相同**（采用 `ustconv --check` 的判据）。
4. 同一串命令执行两次，两次的变更序列逐条相同。
5. 节点 ID 在插入、删除、撤销、重做之后仍指向同一节点。
6. 音源方面：修改一条 oto 条目并保存后，**编码不变**，未修改的条目逐字节不变。
7. **每个节点操作和领域函数都有对应的命令，每条命令都对应到函数。** 由一个将两侧列表对照的测试保证，新增函数而未添加命令时测试失败。

第 3 项是这一层最严格的检验：撤销栈中只要有一处逆操作写错，该项即会失败。

## 不在范围内的事项

- **多轨。** UST 为单轨，`.usth` 的 `tracks` 数组长度恒为 1，见 [`UsthFormat.md`](UsthFormat.md)。树中保留 `/tracks/0/` 这一层，将来开放多轨时语法不变。
- **协同编辑。** 不在规划范围内，不为其做设计。
- **将命令扩展为脚本语言。**
- **让变更记录层理解业务逻辑。** 「量化」「移调」是领域函数，而非变更形状。变更形状只涉及槽位、序列、映射和节点的父子关系。
