# HelloUTAU 使用手册

HelloUTAU 是一款跨平台的第三方 UTAU 编辑器，在功能上尽可能与官方 UTAU 保持一致的基础上，提高用户体验与扩展性。

## HelloUTAU 工程文件

扩展名：`.usth`（完整规格见 [`UsthFormat.md`](UsthFormat.md)）
格式：`json`
编码：UTF-8
格式版本：1

第一版单轨，UST 本身就是单轨格式（`Tracks=1`）。但顶层从一开始就是 `tracks` 数组，将来放开多轨不必改格式版本。

可与 `.ust` 文件相互转换。

### 控制音符

由 `.usth` 生成的 UST 中，第一个音符是 HelloUTAU 保留的音符，歌词固定为 `_USTH_`。它用一个名为 `$usth` 的用户定义条目存放 HelloUTAU 的配置信息。

歌词取这个名字是为了醒目：用户在 UTAU 里一眼就能看出这个音符不是自己写的。**要维持与 HelloUTAU 的兼容，就不要删它。**

这个音符对 UTAU 来说等价于休止符——找不到对应采样，所以不发声、也不占用渲染时间，但它按 `Length` 占据时长。`.usth` → `.ust` 每导出一次加一个，`.ust` → `.usth` 每导入一次恰好吃掉一个。

控制音符中包含 HelloUTAU 的插件配置信息。**不包含编码**，因为只有一种编码，见下。

### 为什么载体必须是音符

这一节的结论都来自对 UTAU 0.4.19 的实测，探针文件和比对脚本留在 `.cache/utau-probe/`，完整记录见 [`docs/claude/utau-ust-preservation.md`](claude/utau-ust-preservation.md)。

| 位置 | `$` 开头的未知条目 | 不带 `$` 的未知条目 |
|---|---|---|
| 音符段 `[#NNNN]` | **保留** | 丢弃 |
| `[#SETTING]` | 丢弃 | 丢弃 |
| `[#VERSION]` | 丢弃 | 丢弃 |

音符段是唯一能留住东西的地方，且必须带 `$` 前缀。UTAU 自己的 `$direct`、`$patch`、`$region` 就是这个命名空间里的实例。

**绝不能自造段落。** 未知段落不会被忽略，而是被 UTAU 当成音符：实测 `[#HUPDATA]` 被转成了一个 `Length=15`、`NoteNum=24`、歌词为空的垃圾音符，后面所有音符索引顺移一位，全程没有任何提示。反过来，HelloUTAU 读到不认识的段名时要当成文件已损坏，不能跳过——用户手里那份已经被 UTAU 改过了。

条目顺序不保留，UTAU 会把未知条目移到段尾，所以不要用位置表达任何含义。同名条目重复时后者胜。

### 载荷格式

条目的值用 **base64url 去掉填充**（字母表 `A-Za-z0-9-_`）。这不是随便挑的：

- `=` 会截断值，所以带填充的 base64 不能用
- 制表符不但截断值，还会把本段其后的所有条目一起带走
- 空格会被替换成逗号
- 值必须是纯 ASCII，因为要先把文件当 ASCII 读、定位到编码声明，才谈得上解码整个文件
- **值不许为空**，空值会被整条删掉，读回来就分不清「没有这条」和「这条是空的」

长度没有实际限制，实测 65536 字符原样保留。

### 往返承诺

分两层，不要混为一谈。

**HelloUTAU 专有信息无损。** 用户在 UTAU 中编辑此 UST 时，只要不动控制音符，保存出的新 UST 可以完整转换回 `.usth`。

**工程本身不保证字节无损，只保证 UTAU 能等价打开。** UTAU 存盘会归一化数值、省略等于默认值的条目、重算 `@preuttr` 一族的只读量。判据是语义等价：两边各自解析成内存模型，规范化后比较。

## HelloUTAU 标记文件

音源文件夹：`hello-config.json`
插件文件夹：`plugin.json`

`hello-config.json` 记录同一目录下 UTAU 原版配置文件 `oto.ini`、`prefix.map`、`character.txt` 的文件编码，以及 HelloUTAU 自己需要在这一层保存的数据。

**一个文件夹一个，不是一个音源一个。** 一个音源可以有多份 `oto.ini` 分散在各级子目录，各自的编码还可能不一致，所以标记文件跟着目录走，和它描述的文件放在一起。这样音源的某个子目录被单独拷走时，编码信息也跟着走。

`plugin.json` 是插件的完整清单，不只是编码。对 HelloUTAU 感知的插件，它取代 `plugin.txt` 成为权威来源。

## HelloUTAU 编码兼容策略

### 工程

`.usth` 永远是 UTF-8，不需要选。

打开别人的 `.ust` 时：文件里有 `Charset=` 就按它，没有就要求选择编码，选定后整个文件转成 UTF-8。

导出 `.ust` 时的编码**可以配置**，默认 UTF-8，每次导出还能单独改。默认取 UTF-8 是因为 Shift_JIS 表示不了中文歌词和中文文件名，一落到转义串就既不好看也不好用；要把文件交给还在用老插件老工具的人时，改成 Shift_JIS。

### 音源库

第一次打开音源文件夹时会要求选择编码，之后编码存在该目录的 `hello-config.json` 中。

### 插件

插件文件夹内没有 `plugin.json` 时，Windows 上按系统 ANSI 代码页读取，其他平台按 CP932——绝大多数 UTAU 插件是日文的，而 ANSI 这个概念在 Windows 之外不存在。有 `plugin.json` 时按其中指定的编码。

### 转义

如果写出去的目标编码表示不了某个字符，用转义串表示。目标是 UTF-8 时用不上，只在导出成 Shift_JIS 这类编码、写插件临时文件、以及写音源配置时才会发生。

转义和还原是同一处代码的两个方向，必须成对，并且转义串本身出现在原文里时也要能正确还原。

## 安全行为

官方 UTAU 直到 2024 年 5 月的 v0.4.19 才修掉两个存在于此前所有版本的漏洞。HelloUTAU 在这两处都比 UTAU 更严格。

**工程文件里的字符串不可信。** 打开一份构造过的 `.ust`，在官方 UTAU 上可以导致执行任意 OS 命令（CVE-2024-28886，OS 命令注入）。具体是哪个字段、经由哪条路径，官方和 JVN 都没有公布。

HelloUTAU 因此在两处都设防，不依赖于猜中那个机制：

- **起进程一律用参数数组，绝不拼成命令行交给 shell。** 官方 UTAU 渲染时默认写一个批处理再执行它（v0.4.12 的更新日志里有「wav生成時にバッチを使用しない」这个开关，说明不关就是用批处理），而批处理是 shell 脚本，工程里取出的文件名、别名、flags 只要含 `&` 或换行就能追加命令。HelloUTAU 不走批处理。
- **工程自带的引擎路径默认不使用。** `[#SETTING]` 的 `Tool1`、`Tool2` 和音符上的 `$patch` 都是工程里写死的路径，照单执行等于让工程指定跑什么程序。HelloUTAU 一律用本地配置里的引擎，除非用户在明确的提示里选择信任。**这些设置仍会被原样保存**——逐工程配置引擎是 UTAU 的正常用法，丢掉它等于删用户的设置。危险的是不问就执行，不是存下来。

**音源与插件的压缩包条目路径不可信。** `.uar` / `.zip` 里的条目名可以是绝对路径或者 `../../..`，官方 UTAU 照着写文件，于是可以往任意位置释放文件（CVE-2024-32944）。HelloUTAU 遇到绝对路径、盘符、`..` 分量或符号链接条目时拒绝整个包并告知用户，而不是悄悄过滤掉。

## 缓存

与 UTAU 保持一致，缓存目录开在工程文件旁边。UTAU 存盘时会把 `CacheDir` 改写成跟随文件名，HelloUTAU 照做。

## HelloUTAU 插件

HelloUTAU 支持四种插件：

- 原版 UTAU 插件：
  - 接受包含当前选区的 `temp.ust` 作为第一个命令行参数的可执行文件，执行选区修改，执行过程阻塞界面
  - 也可以是 `.bat` 脚本。`plugin.txt` 里带 `shell` 键的插件由命令处理器执行，并且像官方 UTAU 一样显示一个可见的控制台窗口，脚本的输出用户能直接看到
- 原版 UTAU 插件的内置版本：
  - 继承自 `RangeEditPlugin` 的 C++ 实例，执行选区修改，执行过程阻塞界面
- 编辑界面扩展插件：
  - 继承自 `EditorExtensionPlugin` 的 C++ 实例，提供额外的编辑界面，执行过程不阻塞界面
- 音源库插件：
  - 继承自 `VoiceBankPlugin` 的 C++ 实例，执行对音源库的批量操作，执行过程阻塞界面
