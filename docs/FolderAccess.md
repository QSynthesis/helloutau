# 文件夹的访问检查

本文档是启动时集中检查受保护文件夹的设计。第五节的三个问题已由作者 2026-10-21 确定，记录、启动检查、集中的提示与设置页已于同日实现，第二节中 macOS 的几点仍待实测。

## 一、动机

作者 2026-10-21 提出：受保护的文件夹（如「文稿」）一律在程序启动时访问一次并记录结果，程序运行中途不再突然弹出系统的授权询问，各处也不必各自判断并报错，因为结果已经记下。

现在有六处各自访问并各自报告：`VoiceBankSource`（打开音源）、`ProjectPropertiesDialog`（音源一栏的列表）、`ClassicPlugin` 与 `ClassicPluginContribution`（「经典插件」菜单与「部分插件无法读取...」）、`InstallArchiveDialog`（安装的目标文件夹）以及 `FileIntegrity`（信任检查读取的程序）。前五处读取的都是音源文件夹与插件文件夹，原因由 `PlatformFileSystem::unreadableFolderReason()` 与 `accessErrorReason()` 给出。

## 二、平台的行为

**macOS 的「文件与文件夹」授权（TCC）。** 未沙盒化的应用首次访问「文稿」「桌面」「下载」、网络卷宗与可移除卷宗中的内容时，系统询问用户是否允许，结果按应用记录，之后不再询问。拒绝后访问以 `EPERM` 失败，`accessErrorReason()` 已为此给出指向「系统设置」的说明。以下几点尚未实测，实施前须在 mac 上确认：

- 询问期间发起访问的调用是阻塞到用户回答，还是立即以 `EPERM` 返回、待用户允许后才可访问。
- 对受保护文件夹中不存在的路径执行 `stat` 是否同样触发询问。
- ad-hoc 签名的应用每个版本的代码签名不同，更新后是否再次询问（`Distribution.md`「macOS 的自动更新」已记为未实测）。

现状是启动时已经访问「文稿」：`AppLoader` 的构造函数从 `Documents/OpenVPI/HelloUtau/Extensions/translations` 载入翻译，插件系统从 `Extensions/plugins` 载入原生插件。因此询问多半已在启动时出现，只是出现的时机由这两处偶然决定，后续访问的失败仍由各处分别报告。

**Windows 的「受控制文件夹访问」。** 开启后，未经允许的应用不能修改「文档」等受保护文件夹中的文件，读取不受影响。写入以拒绝访问失败，Windows 安全中心同时显示通知。HelloUtau 写入「文档」的只有安装音源与插件（`ClassicExtensions/voice`、`ClassicExtensions/plugins`），以及用户在这些文件夹中编辑的音源。本机未开启该功能，行为取自 Microsoft 的文档，尚未实测。

**Linux** 没有对应的机制，检查只发现权限与不存在。

## 三、设计

**检查的对象。** 程序会读取的全部音源文件夹与插件文件夹，即各 `ClassicRoot` 下的 `voice` 与 `plugins`、`VoiceLocations::voiceBankFolders()` 中的其他文件夹，以及用户目录下的 `Extensions/plugins` 与 `Extensions/translations`。不存在的文件夹记为不存在，不为检查而创建。

**写入检查。** 只对程序写入的两个文件夹（`HelloUtauRoot` 下的 `voice` 与 `plugins`）进行：创建并删除一个临时文件。写入检查只在设置页的「重新检查」中进行，启动时不做（作者 2026-10-21 决定），因为受控制文件夹访问开启时，每次写入检查都会让 Windows 安全中心显示一条通知。启动时这两个文件夹只做读取检查。

**检查的时机。** `AppLoader` 在读取设置之后、载入翻译与原生插件之前检查一次，在主线程上进行，使 macOS 的询问固定出现在启动时、第一个窗口之前。设置中的文件夹改变时（UTAU 文件夹、音源文件夹）重新检查改变的文件夹。设置页提供「重新检查」，用户在系统设置中允许访问之后可以不重启程序。

**记录。** `kit::FolderAccessRecord` 在 `hellokit/Support/PlatformFileSystem.h` 中，与 `FileFingerprintCache` 相同，是由 `AppLoader` 持有、以 `instance()` 取得的实例。每个文件夹记录一种状态：可读、可读写、不存在、不可读（附原因）、不可写（附原因）。要检查的文件夹由 `AppSettings::readFolders()` 与 `writtenFolders()` 给出。`PlatformFileSystem::unreadableFolderReason()` 照旧直接检查，并以结果更新已记录的文件夹（`FolderAccessRecord::update()`），不为其他文件夹（如各个音源）增加记录。之后的读取检查不覆盖写入检查的结果。代替文件夹的文件记为不存在，Windows 对文件的列举报告 `ERROR_DIRECTORY`，因此另以 `status()` 判断。

**记录只是提示，不是闸门。** 各处的实际读写照常进行并照常处理错误，因为状态在运行中可能改变：用户在系统设置中允许了访问，外置磁盘接上或拔出，文件夹被创建或删除。实际访问的结果与记录不同时更新记录。记录改变的只是报告的方式。

**集中的提示。** 启动检查发现不可读的文件夹时，第一个窗口显示后以程序内的对话框提示一次（作者 2026-10-21 决定），列出各文件夹与原因，以及允许访问的位置：macOS 为「系统设置 > 隐私与安全性 > 文件与文件夹」，Windows 为「Windows 安全中心 > 病毒和威胁防护 > 勒索软件防护 > 允许应用通过受控制文件夹访问」。

**各处只做静态提示。** 现有的六处不再弹出报错框，只在原有的位置以静态文字提示（作者 2026-10-21 决定）：「经典插件」菜单中的「部分插件无法读取...」一类菜单项、工程属性的音源一栏下方与设置页中的说明文字。打开无法读取的音源、向无法写入的文件夹安装等由用户直接发起的操作，失败时仍须说明原因，这一类不属于启动检查能事先消除的报错，实施时逐处列出并与作者确认。

**设置页。** System Settings 下新设「文件夹访问」页（作者 2026-10-21 决定），列出全部记录的文件夹、状态与原因，带「重新检查」按钮，重新检查时包括写入检查。

## 四、测试

- `test_FolderAccessRecord`：可读、不存在、不可读（POSIX 上去掉权限，root 下跳过，同 `test_PlatformFileSystem`）、不可写各一种，重新检查后状态更新，实际访问的结果更新记录。
- `test_PlatformFileSystem` 增加有记录与无记录两种情形。
- macOS 的询问与 Windows 的受控制文件夹访问无法自动测试，由作者在开启该功能的机器上查看。

## 五、作者的决定（2026-10-21）

1. 集中的提示是第一个窗口之后的程序内对话框。现有各处只做静态提示，如菜单项与设置页中的说明文字，不再弹窗。
2. 写入检查只在设置页的「重新检查」中进行。
3. 状态列表放在 System Settings 下新设的页面。
