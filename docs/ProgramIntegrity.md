# 受信任程序的完整性

> 状态：设计，作者 2026-10-21 审阅通过，尚未实现。

本文档规定 HelloUtau 如何确认一个已受信任的外部程序仍是用户信任时的那个文件：工程中的合成工具（`SynthToolTrust`）与经典插件的程序（`ClassicPluginTrust`）。信任本身的规则见 [`../CLAUDE.md`](../CLAUDE.md)「安全底线」第一条与 [`note.md`](note.md)「安全行为」，本文档只补充信任之后的部分。通用的部分放在 `HelloKitSupport`，两种信任与渲染只是它的使用者（作者 2026-10-21 要求）。

## 动机

作者 2026-10-21 指出两个问题：

- **信任记录可能无限增长。** 现状是同一个合成工具的路径、同一个插件文件夹各只有一条记录，重新信任时替换旧记录。但已删除或移走的程序的记录永远保留，记录的条数随用过的不同路径增长。
- **信任之后替换文件，在一次渲染中仍会运行。** 信任只在开始播放、渲染音轨与准备后台渲染时检查（`ProjectWindow` 的 `projectSynthTools()`），之后渲染为每个音符启动重采样器，不再检查。经典模式由命令处理器执行渲染脚本，进程由脚本启动，HelloUtau 无法在每次启动之前插入检查。插件从检查到启动之间同样有时间差。

另有一处缺陷：`ClassicPluginTrust` 在程序读不出时得到空内容的 SHA-256，并以此记录信任。

## 威胁模型与残余风险

信任防范的是工程文件或插件文件夹让用户未审查过的程序运行（CWE-78 之外的「执行任意程序」，见 `CLAUDE.md`）。完整性检查在此之上保证：用户信任的是哪个文件，运行的就是哪个文件。

- **Windows**：渲染与插件运行期间，HelloUtau 以不共享写入与删除的方式打开程序文件，其他进程无法修改、替换或删除它，检查与运行之间没有时间差。
- **macOS 与 Linux**：系统没有强制锁，不借助 root 无法阻止替换。HelloUtau 在每次启动之前与运行期间每 100 毫秒比较文件身份，发现替换即终止渲染，因此被替换的程序在终止之前最多运行到下一次比较。
- **明确接受的残余风险**（作者 2026-10-21 同意）：在 macOS 与 Linux 上，能在这 100 毫秒内替换程序的，须能以用户本人的身份写入该文件。这样的攻击者本来就能修改用户的设置与 shell 配置，或者替换用户信任过的任何程序，这个时间窗口并不给他新的能力。另一个用户能写入的情形由写权限检查在信任之前拒绝，见「写权限」。

## 组件（`HelloKitSupport`）

四个组件都在一个头文件 `hellokit/Support/FileIntegrity.h` 中（作者 2026-10-21 决定），因为它们回答的是同一个问题，即一个文件是否仍是当初的那个文件，分散在几个头文件中反而要来回查找。实现可以分在几个源文件中。

### `kit::FileFingerprint`

一个文件的身份与内容，不可变的值类型。

- **身份**（`FileFingerprint::Identity`）：Windows 上为卷序列号、文件索引、大小、最后写入时间与更改时间（`GetFileInformationByHandleEx` 的 `FileBasicInfo`），其他系统为 `st_dev`、`st_ino`、大小、`st_mtim` 与 `st_ctim`。重命名替换必然改变文件索引或 `st_ino`，原地写入必然改变 `st_ctim`，后者无法由 `utimes()` 改回，因此改回修改时间也不能隐藏原地写入。身份只用于比较，不写入记录。
- **内容**：SHA-256，小写十六进制，与现有记录的格式相同。
- `FileFingerprint::of(path)` 打开文件，经同一个句柄读取身份并计算 SHA-256，因此身份与内容属于同一个文件。读不出时返回 `std::nullopt` 与原因，不返回空内容的哈希。
- `Identity::of(path)` 只读取身份，一次 `stat`，不读取内容。

### `kit::FileFingerprintCache`

按规范化路径缓存指纹，使重复的检查不再读取整个文件。应用创建一个实例，如同 `QCoreApplication`，由 `AppLoader` 持有，以 `instance()` 取得，与 `TemporaryStorage` 相同（见「kit 层设施」的约定）。

- `fingerprintOf(path)` 是静态函数：先读取身份，与缓存中的身份相同时返回缓存的指纹，否则重新计算并更新缓存。没有实例时直接计算。
- 线程安全，因为渲染线程与界面线程都会查询。
- 一次检查的代价因此是一次 `stat`。渲染开始时的检查、设置页与工程属性中的显示都可以随时调用，不必顾虑读取整个程序文件。

### `kit::FileGuard`

在持有期间保证一组文件仍是指定的内容，不可复制，以 `std::shared_ptr<const FileGuard>` 在线程之间共享。

- `FileGuard::hold(files)` 接受每个文件的路径与预期的 SHA-256，打开每个文件并经该句柄重新计算 SHA-256，与预期不同或读不出时返回 `std::nullopt` 与原因。Windows 上以只共享读取的方式打开（不带 `FILE_SHARE_WRITE` 与 `FILE_SHARE_DELETE`），句柄保持到守护销毁，因此持有期间文件无法被修改、替换或删除。其他系统上保持文件描述符，并记下身份。
- `isIntact()` 重新读取每个文件的身份并与持有时的身份比较，线程安全，代价为每个文件一次 `stat`。在 Windows 上同样比较，以防锁在网络文件系统上无效。
- `changedFile()` 返回第一个发生变化的文件，供报告使用。
- 持有的范围是**一次渲染任务或一次插件运行**，不是工程窗口的生命周期。否则在 Windows 上，工程窗口打开期间用户无法更新自己的重采样器。

### `kit::FilePermissions`

- `writableByOthers(path)` 返回使其他用户能替换该文件的原因，或 `std::nullopt`：文件本身或其所在目录对同组用户或其他用户可写，或者属于当前用户与 root 以外的用户。目录的粘滞位（`S_ISVTX`）使其中他人的文件无法被删除或重命名，因此带粘滞位的可写目录只检查文件。与 ssh 的 `StrictModes` 是同一思路。
- Windows 上总是返回 `std::nullopt`。ACL 的判断复杂且多数用户目录默认只有本人可写，这次不做。

## 信任记录的统一规则

两种信任的记录格式不变：`SynthToolTrust` 记在应用设置的 `synthToolTrust/trusted`，`ClassicPluginTrust` 记在插件设置的用户数据中。规则统一为：

1. **每个键一条记录。** 合成工具的键是规范化路径，插件的键是插件文件夹。重新信任时替换旧记录（现状）。
2. **写入时清理失效的记录。** 写入任何一条信任时，删除所在文件夹存在、程序本身却不存在的记录。所在文件夹也不存在时保留记录，因为那可能是暂时未连接的外置磁盘。
3. **内容一律取自 `FileFingerprintCache`。** 读不出时不记录信任，并告知原因。
4. **写权限检查在信任之前。** `FilePermissions::writableByOthers()` 给出原因时不提供信任，消息框说明原因与修正方法（`chmod go-w`）。

## 接入

- **合成工具**：`SynthToolTrust::isTrusted()` 与 `trust()` 改用缓存。`ProjectWindow` 在每个渲染任务开始时为经由信任而允许的工程合成工具建立 `FileGuard`，随 `kit::SynthTools` 交给运行器。设置中的合成工具不经哈希信任，不建立守护。
- **运行器**：`ThreadedSynthRunner` 与 `RealtimeSynth` 在每次调用 `SynthToolProcess::run()` 之前检查守护，`ClassicSynthRunner` 在执行脚本之前检查。三者传给 `SynthToolProcess` 的 `canceled` 回调都并入 `!guard->isIntact()`，因此脚本运行期间的替换在 100 毫秒内终止脚本及其启动的所有进程，与取消相同。
- **结果**：守护失效时渲染以失败结束，诊断为「重采样器 %1 在信任之后发生了变化，渲染已停止」，与取消区分。信任记录不必显式撤销：变化后的文件指纹不同，下次开始播放时重新询问。
- **插件**：`ClassicPluginRun` 在确认信任之后为插件的程序建立守护，持有到插件运行结束。启动之前检查一次。运行期间显示的是带「取消」的模态对话框（`waitFor()`），对话框以 100 毫秒的定时器检查守护，失效时取消插件运行，与「取消」相同，并报告原因。以 `ShellExecuteEx` 启动、无法观察结束的插件同样如此，守护持有到用户点「完成」。

## 测试

四个组件的测试同在 `test_FileIntegrity`，与头文件一一对应：

- 指纹：重写内容、原地写入后改回修改时间、重命名替换，身份都发生变化。读不出的文件返回 `std::nullopt`。
- 缓存：身份不变时不再读取内容（以计数的测试钩子确认），变化后重新计算。多线程同时查询。
- 守护：Windows 上持有期间写入、重命名与删除都失败。所有平台上修改文件后 `isIntact()` 为假，`changedFile()` 指出该文件。预期哈希不符时 `hold()` 失败。
- 写权限（macOS 与 Linux）：文件或目录 `chmod g+w`、`o+w` 后给出原因，带粘滞位的目录只检查文件。
- 运行器：以替代的 `SynthToolProcess` 在渲染中途替换文件，确认渲染以守护失效结束。经典模式在 Linux 上以一个长时间运行的脚本确认 100 毫秒内终止。
- 两种信任：清理规则与读不出时拒绝信任。

## 接口的一致性

- 四个组件只依赖路径与 SHA-256，不认识合成工具与插件。
- 所有「读不出」都以 `std::nullopt` 加原因返回，不以空字符串或空哈希表示。
- 跨线程使用的只有 `FileFingerprintCache` 与 `FileGuard`，二者的公开函数都是线程安全的。
